# AND-452 统一摘要与版本化方案文档

## 行为与实现

Agent 在生成阶段提炼诊断结论、修改建议和决策边界；详细依据与验证目标进入以相同摘要开头的 Markdown。prepare_plan_document 保存不可覆盖原文，返回各端使用的同一 plan（摘要、固定文档链接与范围说明）。控制台不裁剪或改写该消息，复用 MarkdownText 展示和原位 InlinePlanApproval。

文档存储不依赖节点，GET /api/v1/plan-documents/:id、下载与 MCP get_plan_document 读取相同字节。正文按 Unicode 码点分页；sha256 对原始 UTF-8 字节计算。每次读取核对全部覆盖条目的权限；写入要求原会话、同项目和操作权限。不同客户端或账号的访问能力不以私有节点绑定决定。

request_plan_approval 使用 documentId、原样 plan 和空 validation。文档链接中的不可变 ID 参与现有方案摘要计算；身份、scope、原文同时校验。新版本不能沿用旧按钮。原生签名确认、Web 批准、续办去重及旧文本方案兼容保持。文档读取不触发批准，也不是批准的强制条件。

批准后完整正文可从工具结果或 get_plan_document 取回。append_comment(planDocumentId) 以原始 Markdown 创建附件，以固定 plan 写简短评论；附件和评论各有固定幂等键，失败重试复用。存储写入后重新核对当前权限与批准，避免在异步上传期间沿用失效授权。上传成功而评论失败时不声称归档完成。

## 返工与权限

轮次以真实 verification_failed 事件确定；未领取时也能准备第一轮方案。每轮版本独立，旧原文不可覆盖。原范围补修以 parentDocumentId 引用仍有效的原批准，属于诊断记录，不能作为新方案请求批准或扩大权限。实质变化准备无 parent 的新方案。服务端不能判断自然语言的语义等价，Agent 必须按 Skill 区分补修与范围变化，不得借补修记录绕过审阅。

verification_failed 本身不撤销已批准方案；条目内容修改、Builder 交接、取消、完成后重开等仍按原范围与执行授权失效规则处理。未获批的跨轮次旧文档不能继续批准。方案授权与执行身份保持独立，补修仍需当前有效执行授权。用户选择、交付结果和测试证据追加记录，不倒填获批计划。

## 覆盖入口与规范

Web 控制台和条目会话共用 InlinePlanApproval、MarkdownText；增加固定文档阅读页和原文下载，不新增样式豁免。Node/macOS 的派单及项目会话提示同步引用 Skill；Skill 5.58.0 定义全文流程和旧客户端限制。现有跨端完整性规范按用户明确选择允许统一摘要加当前端可完整读取的固定文档，不改变其他受限审批。
