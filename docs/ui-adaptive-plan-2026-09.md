## 2. 问题：为什么「原来很乱」

现状 ≤1023px 的卡片里，`.item-row-main` 是两列网格 `28px minmax(0,1fr)` + `gap: 12px`
（`styles.css:745`，`align-items: center`）：左列放类型图标，右列放**整个文字块**
（`key + 徽章 + 标题 + 描述` 都在 `.item-copy` 内）。在已入库的 375×812 基线
`list-phone-light-visual-linux.png` 上，逐卡可直接看到三个后果：

**（1）类型图标不与标题对齐。** 图标在左列里按整个文字块垂直居中，所以它相对标题的位置
随该卡有几行文字变化——375 基线上四张卡**一个不落地落在描述行旁边**
（卡 1 的 📄 挨着 `备注。`、卡 3 的 💡 挨着 `灵感：…`），永远不会挨着标题。

**（2）标题的第一行被 key 吃掉宽度。** 标题与 key 是同一个 flex 行
（`.item-title-line`，`styles.css:754`）里的兄弟节点，标题第一行因此少掉
key 宽度加 8px 间距——已入库基线里 key 是 `FX-5`，损失 34px；**真实数据里 key 是
`AND-190` 这类 46.4px 的编号，损失 54.4px**（`AND-190` 上有徽章时标题只剩 33.6px）。

**（3）折行后的第二行不回左缘。** 正文块的左缘在内容左缘 +40px（图标 28 + 间距 12），
而标题第一行因为前面的 key 再右移到 +94.4px（40 + 46.4 + 8；基线里的 `FX-5` 是 +74）；
折行后的第二行回到 +40px。
于是一张卡上出现**三条左缘**：图标 0、正文块 40、标题首行 94。
标题第一行与它自己的第二行都不在同一条线上，这正是「参差」的来源。

三者叠加的结果就摆在基线上：**卡片 3 的标题折行后只剩「时间」两个字，卡片 4 只剩「表」一个字**
——AND-32 给手机标题两行的本意，被第一行的宽度损失吃掉了。

**（4）徽章挤压标题**：徽章带硬下限 `min-width: 5em`
（`.item-dispatch-badge` `styles.css:777`、`.item-handler-badge` `:781`），
且与标题同在一个 flex 行里。375px 上实测真实条目 `AND-190` 的后果：

| 元素 | 需要 | 实际得到 |
|---|---|---|
| 标题 | — | **88px**（一行两三个字） |
| 徽章 `OpenCode · Mac mini` | 130px | **57px，被截掉 73px** |
| context 行 `Chrome 153 · 1776x899` | 134px | 98px |
| context 行 `Web` | 24px | 18px |

即：徽章和标题同时在挨饿，而 `min-width` 只保证徽章不全没，不保证它看得懂。
（v2.1 这张表用的是手编的 `派发失败` 56px，比真实徽章窄一半以上，低估了损害。）

设计稿 08 用**一个**结构改动同时解决 (1)(2)(3)(4)：
把 `图标 + key + 徽章` 归到**元信息行**，标题与描述构成**独立的正文块**，
整体悬挂缩进到类型图标左缘。

（代码层面 (1)(2)(3) 是同一个改动的三个侧面，§4 拆成 UI-21 / UI-22 只是为了验收时
能分别打勾。）

另有三处与设计稿的结构差异：

- **设计稿是独立卡片，现状是一整块面板**。设计稿 08 每张卡 16px 圆角、卡间留空隙露出
  页面底色；现状整张列表是一块白面板，卡与卡之间只有 1px `--line-soft`
  （`styles.css:722`），不漏底色。这是**结构差异、不是尺寸差异**——
  v2.1 曾把它列为「不做」，2026-09-25 用户确认**按设计稿执行**，故上移为 **UI-26**。
- **缩略图在状态行之下**（`grid-row: 3`，`styles.css:1488`），而设计稿放在描述与页脚之间。
- **手机上的时间被整段丢弃**：`.item-updated { display: none }`（`styles.css:1590`）把
  「提交人 + 更新时间」整列在 ≤520px 隐藏，同时用 `.item-context-creator { display: inline }`
  （`:1591`）把提交人挪进 context 行。结果是 375px 卡片上**没有任何时间信息**。
  设计稿 08 的页脚里同样没有时间，所以这不算「偏离设计稿」——但它是真实的信息缺失，
  §4 UI-24 一并处理。

## 3. 设计稿 08 的实测规格（严格对表）

**数据来源换了。** v2.3 及之前是「渲染 PNG 后自己量」——下载的 PNG 只有 235×512，
分辨率不够，量出来的是我估的数。v2.4 改成**取 Stitch 设计稿的原始 HTML**
（`list_projects` → `list_screens` → `get_screen` → `htmlCode.downloadUrl`），
它是一张带 Tailwind CDN 的页面，在 375px 宽的 iframe 里渲染后直接 `getComputedStyle` 读值。

**三列在同一个 375px iframe、同一次会话里量出**，所以下面的 x 可以直接相减。
两个前提先说明，否则数字对不上：

- **可用宽是 360，不是 375。** 375px 的 iframe 里两边都有 15px 滚动条，
  `documentElement.clientWidth` = 360。设计稿的卡片容器是 `main.px-4`，于是卡片
  = 360 − 2×16 = **328**；效果图的 `.workspace` 也给 16px（v2.4 从 15 改成 16），
  所以两边卡片都是 **328，x 都是 16**。
  （v2.3 的「设计稿 343」是 PNG 目测值，错。328 才对。）
  真机是**浮层滚动条**（内容宽 373，卡片 341），所以这些**绝对值**只在这一档成立；
  本节的**对比结论**与帧宽无关——三档（358/360/373）下 Δ 全是 0，见 §1 的说明。
- **设计稿的卡片有 1px 边框**，`box-sizing: border-box`，所以内容盒
  = 16 + 1 + 16 → **x 33 到 327（宽 294）**。

现状列 = 当前代码（`main @ 86aab12`）+ 独立卡片外壳（外壳自带 16px 圆角/1px 边框，
两列都套，所以「圆角」一行两列都是 16）；效果图列 = 本方案改完后的效果图
（`apps/web/public/__card-mock__/after.html`，多选态开，真实数据 10 条）。

而是 6 行 CSS：

```css
.item-select {
  -webkit-appearance: none; appearance: none;
```

⚠️ `padding: 0` 是**必须**的，不是顺手写的：`styles.css` 有一条笼统的
`input, textarea, select { padding: 0 12px }`（给文本输入框的内边距）。在 `border-box` 下，
盒子不可能缩到比 `padding + border` 更小，于是 `12+12` 的 padding 加 `2+2` 的 border
**盖过了 `width: 20px`，框实渲成 28px 宽**——多出来的 8px 是空白，但命中区和视觉重心都跟着偏。
这条是 8× 放大才看出来的：所有 `width` 规则都写着 20px，量出来却是 28px。

未选中态的描边色 `#a3a3a3` 是设计稿的 `neutral-400` 硬编码。深色模式下它偏亮，
要么换 `--line-dark`（`#c8c7bf`）、要么新增一个令牌，**这件事和 §8 开放问题 4 是同一个问题**，
留到那一条一起定。

**一条改法上的分歧，按本方案执行。** 设计稿的正文缩进 `pl-7` = 28px，而它的图标在 x=63、
正文在 x=61——**设计稿自己的正文比图标左 2px**。本方案 UI-22 取「正文与图标同轴」，
在效果图里是 30px（勾选框 20 + 间距 10），比设计稿的 28px 多 2px，正文落在 x=63、图标也在 x=63。
理由见 UI-22：那个 28px 是「勾选框 20 + 间距 8」的副产物，本仓库勾选框与图标同在一条
flex line 上，照抄数值反而会错位。

**顺带查出一个真实缺陷（已修）。** UI-21 把 key 从 `.item-title-line` 移进 `.item-meta` 后，
`styles.css:755` 的 `code` 规则没跟着走，key 会掉到 UA 默认的 **13px monospace**——
效果图第一版就是这个样子，对表时才看出来。改法：规则跟着选择器走（`.item-meta code`），
数值按设计稿取 12px / 600 / `#737373`。

左基准线是**类型图标（x=63）不是勾选框**。这一点已确认按设计稿执行（UI-22）。

## 4. 改动条目

### UI-21 类型图标移入元信息行

把 `.item-title-line` 一分为二，并把**类型图标从正文列移进元信息行**：
元信息行成为 `勾选 + 图标 + key + 徽章 + ⋯`，标题移出该行成为独立一行。

这一步解决 §2 的 (1) 和 (2)：图标不再随文字行数漂移，标题也不再被 key 吃掉第一行宽度。

徽章的 `min-width: 5em`（`:777`、`:781`）**保留**——它原本的作用是「不要缩到看不见」
（见 `:772-775` 的注释），在独立元信息行里不再有挤压标题的副作用。

但元信息行不能固定一行高——真实徽章会把它撑破。实测（375px）：

| 状态 | 元信息行可用 | `AND-190` 需要 | 余量 |
| --- | --- | --- | --- |
| 多选态关 | 250px | 220px（图标 28 + 间距 8 + key 46 + 间距 8 + 徽章 130） | 30px |
| 多选态开 | **197px** | 220px | **−23px，溢出** |

所以元信息行必须能换行。具体换在**哪一层**见下。

**反面证据**（真实数据 `AND-190`，375px，当前代码）：真实徽章是 `OpenCode · Mac mini`，
需要 **130px**，被压到 **57px（丢 73px）**，渲染成 `Open…`。这正是 UI-21 要解决的问题。

> v2.1 这里用的是手编的 `派发失败`（56px），它比真实徽章**窄**，所以当时低估了损害。
> 真实徽章来自 AND-190 / AND-186 的时间线，格式是 `{agent} · {node}`
> （`itemHandlerBadge`），最坏情况 130px。

#### 图标必须**在编号行之内**，换行才不至于把它挤歪

v2.1 的结论是「`.item-meta` 不换行、把换行权交给内部的 `.item-title-line`」。多选态实测
证明这**仍然会错位**——偏差只是从「图标被孤立」变成了「图标居中到中缝」：

| 图标的位置 | 它居中的对象 | 偏差（key cy − icon cy） |
|---|---|---|
| `.item-title-line` 的兄弟 | 那个元素折成两行后的**整块** | **11px**（改前实测 icon cy 57 / key cy 46） |
| **编号行自己的 flex item** | 第一行 flex line | **0px** |

原因：`align-items: center` 只保证「每个 item 在自己的 **flex line** 内居中」。图标若在
`.item-title-line` 之外，它居中的对象就是那个元素的总高；徽章一旦把它撑成两行，
图标就居中到了两行的中缝上。

所以要把**类型图标放进编号行内部**，作为它的第一个 flex item，由编号行自己换行：

```
.item-row-main
  .item-copy
    .item-meta      ← flex; align-items: center; flex-wrap: wrap; gap: 4px 8px; min-height: 28px
      icon  key  [徽章]
    .item-title
    .item-description
```

徽章折到第二行时，第一行仍只有 `图标 + key`，两者在同一条 flex line 上居中，**偏差恒为 0**。
这同时保证 key 永远不会与它的图标分家——v2.1 那种嵌套写法做不到这一点。

**实测（375px、多选态开、真实数据 10 条）**：`key cy − icon cy = 0`，
**包括徽章折行的 `AND-190`**（元信息行 49px、徽章 130px 落在第二行 badge y=72，
而 icon 与 key 同在第一行 cy=54）。元信息行溢出 0px。

同时把 `.item-copy { gap: 3px }`（`:753`）改为 6px，对齐设计稿的标题↔描述间距。

#### 桌面端会一起坏，补偿规则要落在基准规则上（两个断点都要）

`.item-row-main` 这段 JSX 是桌面与手机**共用**的（`App.tsx:1876`），而且它的两列栅格
`grid-template-columns: 28px minmax(0, 1fr)`（`:745`）是**基准规则**——手机块里只覆盖了
`min-height`（`:1539`），没有覆盖栅格。所以图标一移走，`.item-row-main` 在两个宽度上都
只剩一个子元素，`.item-copy` 都会掉进**那 28px 的第一列**，整行被压扁。

2026-09-25 在 1024px 的真实应用上注入同款 DOM 变化，实测：

| | `.item-copy` 宽 | 溢出 | 行高 |
| --- | --- | --- | --- |
| 只移 DOM | **28px** | 内容 49px 被裁 | 72px |
| 移 DOM + `.item-row-main` 改单列 | 205px | 0 | 72px |

⚠️ v2.3 把这条补偿写成 `@media (min-width: 1024px) { … }`，**那样手机端会漏掉**——
`:745` 是基准规则，手机同样吃那 28px。正确做法是直接改 `:745` 本身（单列，
或等价地让 `.item-row-main` 不再承担栅格），所以**效果图里用的就是不分断点的
`.item-row-main { display: block }`**。桌面宽度仍需单独回归。
副作用：桌面端 key / 标题左移约 17px（key x 309 → 292），间距从 40px 收到 23px。
若不愿动桌面，UI-21 只能退回 v2.1 的写法并接受换行时 11px 偏差——两者不可兼得，
见 §8 开放问题 6。

#### 多选态：勾选框必须与图标同轴，且 44px 命中区不能参与布局

`.item-row-lead` 是 flex 且 `align-items: center`、`gap: 11px`（`styles.css:741`；`:1458`
只给它定位）。把 44×44 的命中区当成 flex item 放进这一行，它比 20px 的勾选框各边大 12px，
于是**勾选框被推到列中间、图标被顶到右边**——这个偏差在图标搬进元信息行之后会被放大，
因为该行只有 28px 高，而命中区仍是 44px。

下面四列是**实测**（375px、多选态开、真实数据；「只改 DOM」= 图标已进元信息行，
「只加对齐」= 再把 `.item-row-lead` 改成 `flex-start`）：

| 量 | 现状（图标还在正文列） | 只改 DOM | 只加对齐 | 设计稿 = 正确做法 |
|---|---|---|---|---|
| 勾选框 cy − 图标 cy | 0 | **+60.4** | **+8** | **0** |
| 勾选框左缘 − 内容左缘 | +12 | +12 | +12 | **0** |
| 勾选框右缘 ↔ 图标左缘 | 23 | 22 | 22 | **10** |
| 图标左缘 − 内容左缘 | 55 | 54 | 54 | **30** |

读法：现状那列看起来「cy 对上了」，那是因为图标当时还在正文列、两者都被同一个高块
居中——**一旦按 UI-21 把图标搬进 28px 的元信息行，勾选框就会掉到图标下方 60px**
（`flex-start` 只能压到 8px）。而左缘 +12 和间距 23 在四个状态里一直没对过。

正确做法是**让命中区退出布局**：勾选框拿到自己的 20px 列和 28px 行高（与图标同高），
44px 的触控面积用一个不占位的伪元素往外扩：

```
.item-row-lead { align-items: flex-start; gap: 10px }   /* 10px = 设计稿 space-x-2.5 */
.item-select-hit { width: 20px; height: 28px; position: relative }
.item-select-hit::before { content: ""; position: absolute; inset: -8px -12px }  /* 44×44 */
```

**实测**：10 条全部 `勾选框 cy − 图标 cy = 0`、`勾选框左缘 = 内容左缘`、
`勾选框↔图标 = 10px`、`图标左缘 = 内容左缘 + 30`，命中区仍是 44×44。
这四项与设计稿逐项相同（见 §3）。

⚠️ 这条和 UI-21 的图标迁移必须**同批**做：图标进了元信息行之后，「勾选框跟谁对齐」才
有意义；单独做任一条都会得到一张仍然错位的卡片。

### UI-22 正文块悬挂对齐到图标左缘

正文块（标题 + 描述）的左缘与**类型图标左缘齐平**——为此不需要加任何缩进。

`.item-row-main` 由两列网格 `28px minmax(0,1fr)` + `gap: 12px`（`:745`）改为
`display: block` 的上下两块即可：图标进了元信息行（UI-21），正文块本来就是块级元素，
它的左缘自然落在 `.item-row-main` 的左缘，也就是图标的左缘。

**注意不要照抄设计稿的 `pl-7`（28px）**。设计稿里勾选框与图标同在元信息行，
`pl-7` 正好等于「勾选框 20px + 间距 8px」，作用是把正文推到图标左缘——它是设计稿
那一行的产物，不是一条要复制的数值。本仓库的勾选框在 `.item-row-lead` 里、
位于 `.item-row-main` 之外，图标已经在 `.item-row-main` 的左缘，再加 28px 反而会错位。

这也顺带解决 (3)：折行后的第二行回到这条基准线，不再跟着第一行的起始位置飘。

**验收**（两项都是同一张 375px 截图上可量的事实）：

- 类型图标坐在元信息行里、与 key 同排，不再出现在描述行旁。
- 标题（含折行后的第二行）左缘 x 与类型图标左缘 x 之差 ≤ 2px。

### UI-23 缩略图上移

`.item-media-strip` 由 `grid-row: 3`（`styles.css:1488`）移到页脚之上，紧随描述。

**缩略图尺寸保持 84×96 不变**——理由见 §5.2。
缩略图间距由 8px 改为 10px，对齐设计稿。

`.item-media-strip.empty-slot { display: none }`（`:1489`）已存在，无附件的卡片不会
因此留下一段空白行。

**验收**：有附件的卡片上，从上到下依次为 元信息行 → 标题 → 描述 → 缩略图 → 页脚。

### UI-24 页脚：分隔线 + 溯源簇 / 状态簇，时间回归

页脚成为**独立一行**，带上方的 1px 分隔线（设计稿本来就有，现状没有）。

```
───────────────────────────────  1px 分隔线
Web · 梁国生 · 3 小时前      ● 已完成  低
└──── 溯源簇（弹性可截断）───┘  └─ 状态簇（定宽）─┘
```

三条规则：

1. **状态簇（状态胶囊 + 优先级）`flex: 0 0 auto` 永不压缩。** 它是「这条现在怎么样」，
   是扫读的第一落点，被挤掉就等于卡片失效。
2. **溯源簇（平台 · 提交人 · 时间）里只有提交人可截断**（`flex: 1 1 auto; min-width: 0`），
   平台与时间均为 `flex: 0 0 auto`。截断的代价不对称：提交人截成 `guoshengli…`
   仍可辨认且不误导；时间截成 `3 小时…` 则完全失去意义，而时间正是判断
   「这条是不是卡住了」的关键。
3. **时间用相对时间。** `formatTime`（`i18n.tsx:1741`）已经是相对时间：
   `刚刚` / `N 分钟前` / `N 小时前` / `N 天前` / `9月24日`，最长约 48px。
   它短、语义是「新鲜度」，比绝对时间更适合手机页脚。

分隔点沿用 `·`——`.item-context small::before { content: "·" }`（`styles.css:1484`）
已经在用，而 `|` 会和页脚上方那根 1px 分隔线打架。

**这需要改 JSX，不只是 CSS**：`.item-updated` 现在是「提交人在上、时间在下」的两列竖排
（`styles.css:782`），内容在 `App.tsx:1954-1956`。改动是把 `creator` 与
`formatTime(item.updatedAt)` 从 `.item-updated` 里取出，接进溯源簇。桌面表格沿用
`.item-updated` 不变（见 §8 开放问题 2）。

**顺带删除两个特例**（新页脚生效后它们不再需要）：

- `.item-updated { display: none }`（`styles.css:1590`）—— 时间不再被丢弃。
- `.item-context-creator { display: inline }`（`:1591`）—— 提交人不必再「搬家」进 context 行。

**375px 的空间算术**（真实数据实测，非估算）：

| 项 | 实测 |
|---|---|
| 页脚内容宽（16px 内边距 × 2 之后） | **294px** |
| 状态簇（状态胶囊 + 优先级） | 77–88px |
| 溯源簇可用 | **196–207px** |
| 最宽的短溯源簇 `Android · AI · Claude Code · 12 小时前` | 214px → **超 18px** |

**v2.1 的结论「三元素单行放得下」只在手编数据上成立**，真实数据推翻了它。

#### 提交人不得压缩（真实缺陷）

v2.1 的规则是「只有提交人可截断」（`flex: 1 1 auto; min-width: 0`）。真实数据证明这条是错的：

| 条目 | 署名 | 需要 | 得到 | 损失 |
|---|---|---|---|---|
| AND-183 | `AI · OpenCode · DeepSeek V4.1 Flash` | 204px | 82px | **122px** |
| AND-146 | `AI · Codex · LGS-MACMINI` | 146px | 82px | 64px |
| AND-150 | `AI · Claude Code` | 97px | 82px | 15px |

**10 条里 3 条**被截断，且截断的永远是 AI 条目——因为复合署名（`AI · 客户端 · 模型`）
天然比人类署名长。一个被截成 `AI · OpenCo…` 的署名**不指向任何人**，
和没有署名一样没用。而且截断是静默的：界面上看不出这里少了一段。

两条修正：

1. **列表中把 AI 署名缩写为 `AI · {客户端}`**（`AI · OpenCode`、`AI · Codex`、`AI · Claude Code`），
   完整署名保留在 `title` 属性和详情页里。列表中够用——列表要回答的是「谁在动这条」，
   客户端就够了；模型名是详情页的问题。
2. **溯源簇内的元素一律 `flex: 0 0 auto` 不收缩**，`.item-footer` 改 `flex-wrap: wrap`，
   装不下时让**状态簇换到第二行**，而不是压扁署名。

**代价**：10 条真实数据在 375px 下实测 **3 条换行**（其中 2 条原本就靠截断才没换行）。
换行只发生在罕见的超长署名行上，比「每一条 AI 条目都悄悄丢掉署名」划算。

> v2.3 这里写的是「375px 上 1 行换行」，那是**目测估的**，实测是 3 条、且这 3 条卡各高
> **+21px**（页脚多一行）。3 条换行是否可接受，见 §8 开放问题 8。

**更窄屏兜底**：容器宽 ≤400px 时整段隐藏提交人，溯源簇退化为「平台 · 时间」。
用**容器查询**实现，不新增 `@media` 断点（`scripts/check-styles.mjs:43` 只允许 `520 / 1023 / 1280`）。

**验收**：375/360/320px 三档下，署名截断条数 **0**；375px 换行行数 **≤3**（实测值，
不是 1——见上的更正）。

### UI-27 ⋯ 按钮去掉方框、改用竖三点

设计稿的更多按钮是**裸的竖三点**（⋮），应用里它是一个带边框的方按钮：
`<summary class="secondary-button">` 提供方框（`styles.css:410-418`：
`background: var(--surface-strong)`、`border: 1px solid var(--line)`、`border-radius`），
图标是 lucide 的 `MoreHorizontal`（横三点，`App.tsx:31`）。

三处改动：

| 项 | 现状 | 改为 |
|---|---|---|
| 图标 | `MoreHorizontal`（`App.tsx:31`），`size={18}` | `MoreVertical`（⋮），**`size={16}`** |
| 方框 | `.row-more-menu > summary` 承自 `.secondary-button` | `background: transparent; border: 0; border-radius: 0` |
| 横向位置 | 44px 命中区齐内容右缘 → 圆点中心 = 内容右缘 **− 22** | 右移 **10px**，圆点中心 = 内容右缘 **− 12**（= 设计稿） |
| 纵向位置 | 44px 命中区在正文块里居中 → 圆点中心 = 图标 cy **− 17** | 上移 **10px**，圆点中心 = 图标 cy **− 2**（= 设计稿） |

**关于圆点粗细**：设计稿画的是 `r=2` **实心**圆（直径 4/24 → 16px 下 2.67px）。lucide 的
`MoreVertical` 是 `r=1` **描边**、`stroke-width: 2`，外径同样是 4/24 → **16px 下正好 2.67px**。
所以只要把 `size` 从 18 收到 16，粗细自动对上，不需要改成 fill。

**横向的 10px**：设计稿的按钮是 24×24 且**齐内容右缘**，但它的 svg 是 16×16、外面还包着
`p-1`（4px），所以圆点中心在右缘内 **12px**。本仓库命中区是 44×44（触控下限，见 §5.5），
齐右缘时圆点中心落在右缘内 **22px**——差 10px。要让**圆点**而不是按钮对齐，命中外扩 10px。

**纵向的 10px，其中 2px 是设计稿自己的选择**：设计稿的元信息行是 `items-start`，
24px 的按钮与 28px 的图标**顶对齐**，于是圆点中心落在图标中心上方 **2px**——不是对齐的。
本仓库的 44px 命中区如果与元信息行居中，圆点会与图标中心**齐平**（差 0）。
两段加起来：先补 `44/2 − 28/2 = 8px`（让 44px 的盒子跨在 28px 的图标上），
再补那 2px，共上移 10px。

> 这 2px 是**刻意跟随设计稿**的，不是误差。若认为圆点与图标齐平更好看，把这 2px 去掉即可
> （`margin-top` 从 −10px 回到 −8px），其余不动。

**命中区保持 44×44**（`styles.css:1492`），只去掉外观方框——设计稿的 24×24 低于触控下限（§5.5）。
外扩后命中区右缘 = 内容右缘 + 10px，落在卡片自己的 16px 内边距里，不溢出、不被裁。

**实测（375px，多选态开与关）**：10/10 行 `⋯ 圆点中心 = 内容右缘 − 12` 且
`= 图标 cy − 2`，与设计稿两值相同；方框已消失
（`border-width: 0px`、`background: rgba(0,0,0,0)`）。

#### 多选态：勾选框的可见性

设计稿的每张卡前面**常驻**一个多选框；应用里勾选框是**逐行按状态**决定要不要渲染的，
不是全局多选模式，也没有对应的 CSS 开关：

```
selectionVisible={item.status === "pending_verification"
  || item.status === "in_progress"
  || (selectedProductCanUseAI && isDispatchable(item.status))}
```

（`App.tsx:1522-1524`，渲染在 `App.tsx:1863` 的 `{selectionVisible && …}` 里。上两版
曾把它写成 `.select-on .item-select-hit` 的 CSS 切换，那是效果图里的类，应用里没有。）

**本方案不改这个行为。** 常驻勾选框的代价在 UI-21 之后已经变小——勾选框的 44px 命中区
改用 `::before` 外扩、不再占布局，所以常驻一行只多占 **勾选框 20px + 间距 10px = 30px**，
而不是旧写法的 44px；但它仍会把元信息行从 195px 压到 165px，等于又回到本方案要修的
那个溢出问题。效果图默认打开多选态（`select-on` 是效果图自己的类），只是为了对齐设计稿的画面。
是否要改成常驻，见 §8 开放问题 7。

### UI-28 勾选框改用设计稿的外观

**v2.3 曾把这条列为「不采纳」**（v2.3 §3「两条不采纳」第 2 条，v2.4 已改为一条），理由是「设计稿是画出来的
`div`，应用是原生 `<input>`；改成画出来的框等于自己维护选中/禁用/焦点三态，收益只有
一个未选中的描边色」。**这个理由是错的**：两边的差不是颜色，是**控件本身**。

8× 放大实测（`apps/web/public/__card-mock__/check.html`，三格共用同一锚点）：

| | 设计稿 08 | 现状 | 改版后 |
|---|---|---|---|
| `appearance` | `none` | **`auto`** | `none` |
| 边框 | `2px rgb(163,163,163)` | **`0px`**（画在 UA 内部，量不到） | `2px rgb(163,163,163)` |
| 圆角 | `4px` | **`0px`** | `4px` |
| 未选中底色 | `#ffffff` | **`#fbfaf7`**（`--surface`） | `#ffffff` |

改动就是给 `.item-select` 换皮，**不动标记，也不自己维护状态**——`appearance: none`
之后真正的 `<input type="checkbox">` 还在，`checked` / `indeterminate` / `disabled` /
`:focus-visible` 四态仍由浏览器给出，只有皮是我们的：

```css
/* styles.css:743 的 .item-select 处 */
.item-select {
  -webkit-appearance: none; appearance: none;
  width: 20px; height: 20px; margin: 0; padding: 0;
  display: grid; place-items: center;
  border: 2px solid #a3a3a3; border-radius: 4px; background: #fff;
}
.item-select:checked { background: var(--mint-dark); border-color: var(--mint-dark); }
.item-select:checked::after {
  content: ""; width: 9px; height: 5px; margin-top: -2px;
  border-left: 2px solid #fff; border-bottom: 2px solid #fff;
  transform: rotate(-45deg);
}
.item-select:indeterminate { background: var(--mint-dark); border-color: var(--mint-dark); }
.item-select:indeterminate::after {
  content: ""; width: 9px; height: 0; border-top: 2px solid #fff;
}
.item-select:focus-visible { outline: 2px solid var(--mint-dark); outline-offset: 2px; }
.item-select:disabled { opacity: 0.38; }
/* 深色模式：描边色待定，见 §8 开放问题 4 */
```

⚠️ **`padding: 0` 是必须的，不是顺手写的。** `styles.css` 有一条笼统的
`input, textarea, select { padding: 0 12px }`（文本输入框的内边距）。在 `border-box` 下
盒子不可能缩到比 `padding + border` 更小，于是 `12+12` 的 padding 加 `2+2` 的 border
**盖过了 `width: 20px`，实渲成 28px 宽**——多出来的 8px 是空白。这条只有 8× 放大才看得见：
所有 `width` 规则都写着 20px，量出来却是 28px。**效果图第一版就带着这个 bug**，
所以 §9 那几行的 `勾选框↔图标` 会在实现后重新量一遍确认。

未选中态的描边色 `#a3a3a3` 取自设计稿的 `neutral-400`，是硬编码。深色模式下它偏亮，
换 `--line-dark`（`#c8c7bf`）还是新增令牌，与 §8 开放问题 4 一起定。

## 5. 已评估、决定不做

§5.6（卡片独立化）已在 v2.2 上移为 §4 UI-26，下面保留其现状记录。

### 5.1 平板与折叠屏双列卡片

**当时的判断**：768×1024 的 `list-tablet-light-visual-linux.png` 上，单列卡片横向拉开到
736px，标题只占左边约 40%，中间大片空白——对应设计稿 04 批评的
「直接横向拉长导致的信息密度失真」。折叠屏展开后的内屏大致落在 700–900 CSS px，
正是这段区间。

**留下的测量数据**（若以后重新评估，从这一步继续，不必重测）：

| 视口 | `.item-list` 宽 | 当时拟定的列数 | 单卡宽度 |
|---|---|---|---|
| 375（手机竖屏） | 343px | 1 | 343px |
| 768（平板竖屏） | 736px | 2 | 362px |
| 820（折叠屏展开） | 788px | 2 | 388px |
| 1023（断点上限） | 991px | 2 | 490px |

宽度的算法：视口减去 `.workspace` 两侧各 15px 内边距，再减去 `.list-surface` 左右各 1px 边框。

**当时论证过的两点**（结论仍成立，供参考）：

- 双列**不会**重蹈 AND-6 的覆辙——那次作废是因为压缩了卡片内部（隐藏摘要、缩小缩略图），
  而双列不压缩内部：768px 下单卡 362px，比手机卡的 343px 还宽 19px，
  两行摘要、84×96 缩略图原样适用。变的只是「一屏放几张」。
- 双列**不能用媒体查询**实现。只能容器查询——正是[设计规范](design-system.md) §7 待补规范
  第 2 条「其余组件内的适配一律改用容器查询」的要求。

**与复盘文档 §6 的关系**：那条非目标「不做平板专属布局。平板沿用紧凑外壳」**保持不变**，
无需修改。本方案不再与它冲突。

### 5.2 缩略图改为 80×80 正方形

设计稿 08 的缩略图是 80×80 正方形，现状是 **84×96 竖版**（`styles.css:1490`）。

**决定不改，保留 84×96。** 两个理由：

1. 设计稿的方形**面积更小**（6400 vs 8064 px²）。AND-6 那次指标作废的教训正是
   「缩略图小到认不出」（见 [界面改版迭代计划](ui-iteration-plan.md) §8），
   照抄会把刚补上的可辨识度再削一次。
2. 真机截图是竖长比，方形裁切（`object-fit: cover`）比竖版更容易把内容切掉。

设计稿的 80×80 是在画板里画的示意图，不是真机截图的容器。

### 5.3 页脚拆两行

第一行平台 + 时间、第二行状态。**不做**：每卡 +19px（一行 11px 文字加行高），
375px 一屏少约半条；且与设计稿的单行页脚不符。

v2.1 在此写过「UI-24 已证明单行放得下」——**真实数据推翻了它**。但正确的解法不是
把页脚**固定**拆两行（那是每张卡都多一行），而是让它在装不下时**自己换行**
（UI-24）：只有超长署名的那几行 +19px，其余保持单行。

### 5.4 时间放进元信息行

把时间放在 key 右侧。**不做**：元信息行正是 UI-21 要从拥挤中救出来的地方，

## 6. 为什么作用域是 ≤1023px

设计稿 08 是手机稿，但卡片布局在 ≤1023px 是**同一套**（`.item-row` 在
`styles.css:1451` 一次性定义，手机断点只在 `:1586` 调列数）。
本方案改的是这套共用的卡片内部，所以平板竖屏（768–1023）会一并受益。

这**不构成**「平板专属布局」——没有为平板新增任何形态，只是同一张卡片本身变清楚了，
与复盘文档 §6 的非目标不冲突。

桌面表格（>1280px）与窄列表栏（`styles.css:843`，≥1280 打开详情时）
**完全不受影响**：本方案的规则都写在 `@media (max-width: 1023px)` 内。

## 8. 开放问题

1. **标题 15px 会不会让两行标题更容易溢出？** 现状 14px、行高 1.35、`-webkit-line-clamp: 2`。
   改 15px 后同样的两行能容纳的字符少约 7%，长标题会更早截断。落地时用种子数据实测：
   375px 下 0/5 条出现「第二行也被切断」。
2. **`.item-updated` 在桌面表格里的样式是否要跟着改？** UI-24 只改 ≤1023px 的页脚，
   桌面仍用 `:782` 的两列竖排（提交人在上、时间在下）。两处样式会分叉，需确认可接受。
3. **本文与复盘文档的关系。** 本方案是复盘文档 §5.2 设备矩阵里
   「手机」一列的具体化，但条目编号独立（UI-21+）。是否需要在复盘文档里回链，待定。
4. **暗色模式下卡片的边框与投影。** 设计稿的 `1px rgba(229,229,229,.6)` 与
   `0 2px 8px rgba(0,0,0,.04)` 是浅色主题下的值，**本仓库有 `--line-soft` 等令牌**。
   实测暗色画布为 `#10161f`、卡片为 `#1d2732`，靠在这两个值之间的浅色描边几乎看不见，
   投影也近乎全黑叠全黑。**建议落地时改用令牌**，但令牌的**具体取值需要设计确认**——
   13px 的边框在暗色下该有多亮，不是一个能靠代码决定的问题。
   **UI-28 之后这条多一个同源问题**：勾选框未选中态的描边是设计稿的 `neutral-400`
   `#a3a3a3`，同样是浅色硬编码，暗色下偏亮。三个候选：原样 `#a3a3a3`、
   复用 `--line-dark`（`#c8c7bf`）、或为控件新增一个令牌。与卡片边框一并定。
5. **密度要不要再挽回。** 真实数据下平均行高从 194.0px 升到 260.9px，一屏从 3 条掉到 2 条。
   上升来自两个真实因素（描述两行、卡片外壳 14px 间距），不是 CSS 回归，
   但它确实牺牲了密度。可选杠杆有三个，都需要确认：
   描述 `line-clamp` 从 2 行收到 1 行（信息损失最大）、
   卡片内边距在手机档收到 14px（偏离设计稿）、
   卡间距从 14px 收到 10px（偏离设计稿）。**本方案暂不选任何一项**。
6. **UI-21 要不要顺带改桌面**（2026-09-25 新增）。图标移进编号行才能让
   「图标 ↔ key 居中」在徽章折行时仍成立（偏差 11px → 0px），但这段 JSX 桌面共用，
   而那条 28px 栅格是**基准规则**（手机端也吃），不改就会两边一起裁。两条路：
   **(a)** 改 `:745` 为单列（两个断点同时生效），代价是桌面 key/标题左移约 17px，
   需单独回归；**(b)** 图标留在原处，退回 v2.1 写法，接受折行时 11px 偏差。
   本方案倾向 **(a)**，但桌面是「不改」的非目标（§7），所以要用户拍板。
   **落地实测（2026-09-25）：走了 (a)，而「约 17px」估高了——1440×900 实测左移只有 4px**
   （`.item-row-main` 由 `28px minmax(0,1fr)` 两列栅格改成单列 flex 后，
   key/标题 x 从 319 到 315；图标本身不动）。桌面表格的其余量（行高、六列栅格、
   gap、padding）**全部保持不变**，见 §9。「4px 是否可接受」仍需用户拍板。
7. **多选框要不要常驻**（2026-09-25 新增）。设计稿每张卡前面都有多选框，
   应用里它**逐行按状态**渲染（`App.tsx:1522-1524`），不是全局多选模式。
   常驻一行会多占勾选框 20px + 间距 10px = 30px（UI-21 之后命中区已不占布局，
   不再是 44px），但仍会把元信息行从 195px 压到 165px。
   本方案默认**保持现状（按状态可见）**，效果图默认打开多选态只是为了对齐设计稿画面。
   **落地实测（2026-09-25）：走了默认路径，并修掉一个它带来的副作用**——
   30px 缩进原本无条件加在 `.item-footer` 与 `.item-media-strip` 上，
   于是**没有勾选框的行**页脚相对自己的标题右移 30px（375px 实测：标题 x 32、页脚 x 62）。
   现改为 `.item-row.has-select` 才缩进，两种行各自与标题同轴。
   「要不要按设计稿常驻勾选框（统一左轴、代价是元信息行 195→165px）」仍待用户拍板。
8. **页脚换行 3/10 条要不要接受**（2026-09-25 新增）。UI-24 的规则 2 用「换行」换掉了
   「截断」，好处是 4 条 AI 署名不再被静默裁掉，代价是 375px 下 **3 条**页脚折成两行
   （每张 +21px 高）。v2.3 估的是「1 行」，那是目测，实测是 3。若 3 条太多，可选：
   把缩写再缩短（去掉 `AI · ` 前缀，只留客户端名）、或对超长署名允许 `text-overflow: ellipsis`
   回到截断（但那正是要修的问题）。**本方案倾向接受 3 条**，请用户确认。
9. **容器宽 ≤400px 时整段隐藏提交人的兜底，落地时没做**（2026-09-25 新增）。
   手机档的卡片**不是**容器查询上下文（`container-type` 只加在 ≥1280 的 `.list-pane` 上），
   所以这条规则在手机上永远不会命中；要在手机上生效得给 `.item-row` 加 `container-type`，
   而那会让卡片内部多一层包含块。任何可辩护的阈值（360px 以下）都会在 360px 手机上

   目前用的兜底是页脚 `flex-wrap`：一行放不下就把状态簇换到第二行（见 §8 问题 8）。
10. **FAB 压住最下面那张卡的 ⋯ 按钮**（2026-09-25 新增，**非本轮引入**）。
    375px 与 768px 截图都能看到：右下角固定 FAB 正好落在视口底部那张卡的 ⋯ 命中区上，
    被压住期间点不到该行的更多操作。卡片变高（本轮）让压住的概率变大，但 FAB 是
    固定定位、`.item-row-actions` 在卡片右上角，这个冲突在改动前就存在（§7 非目标：不改 FAB）。
    可选：给列表底部留出 FAB 高度 + 间距的 `padding-bottom`。**待用户确认是否单独立项。**
11. **`creatorShort` 的缩写口径要不要更短**（2026-09-25 新增）。落地把
    「取前两段」抽成了 `comment-summary.ts` 的 `creatorShort()` 并加了单测

### 9.1 视觉回归套件的一个盲区（2026-09-25 实测）

`playwright.config.ts:33` 的 `maxDiffPixelRatio: 0.01`：375×812 的截图约 30.5 万像素，
容差 ≈ **3,045 px**。而「一条 15px 高的短页脚整行横移 30px」只改约 **400–600 px**，
于是本轮首轮的错位在 `--project=visual` 下**全绿通过、且不重写基线**——
`toHaveScreenshot` 比不过阈值就不落盘，所以「30 passed」不能证明没有位移。
本轮的验证因此改用 **DOM 实测（`getBoundingClientRect`）** 与**删掉基线后重渲染**两条独立路径。
若要这个套件真能拦住这类回归，需要把容差调到 `maxDiffPixels ≤ 100` 量级。

### 9.2 桌面列表与窄列表栏的回归（2026-09-25 实测）

§8 开放问题 6 遗留的「桌面宽度仍需单独回归」本轮补上，同时改掉 PC 列表的两处观感问题。

| 项 | 改前 | 改后（DOM 实测） |
| --- | --- | --- |
| 桌面表格行高（1440×900） | 固定 `height: 72px`、`padding: 0 16px` | `min-height: 72px` + `padding: 14px 16px` → **每行 102px** |
| 元信息 / 标题 / 描述的行距 | `.item-copy { gap: 3px }` | `gap: 4px`（设计稿 `space-y-1`） |
| 桌面不变量 | — | 列宽 `462px 146px 168px 112px 118px 34px`、`gap: 14px` 未动 |
| 窄列表栏（≥1280，面板 ≤648px 即容器查询） | 隐藏描述与创建者/时间，平台与创建者并成一行 | 与宽列表同构、只折行：描述、缩略图、环境·状态、创建者·时间全部保留，顺序一致（340px 面板下每行 162px，带缩略图 252px） |
| 详情打开、面板 ≥648px | 同上（三列 + 缩略图跨行） | 折两行：描述留在标题下，创建者·时间在右上，环境与状态在第二行（700px 面板下每行 125px） |
| 手机紧凑卡片（≤1023px） | — | **未变**：`padding: 16px`、`.item-copy { gap: 6px }`、卡片底色/边框/圆角实测与改前一致 |

102px 高于设计稿的 77px，是**保留三行文本**的必然结果：设计稿把 key 与标题并成同一行
（`flex items-center space-x-1.5`），而本轮按 AND-32 保留元信息 / 标题 / 描述三行，
只把上下内边距补回来（**14px**，比设计稿的 `py-4` 少 2px）与 `space-y-1` 的 4px 行距取回，
行高交给内容决定。两者不可兼得；若要贴到 77px，需回到「key 与标题同行」的两行结构。
