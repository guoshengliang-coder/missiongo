# AND-381 / AND-393：返工派单与旧执行停止核实

> AND-414 已替代本文的强制逐条核实流程：未知状态仅提示，实际活动仍阻塞，接手以条目级授权隔离。本文保留 AND-381/393 历史契约；当前行为见 [执行接手](and-414-execution-takeover.md)。

条目处理轮次、会话的进展上报、原生连接健康和实际执行活动分别判断。`completed` 不能单独证明进程停止；`unavailable` 也不能说明进程正在运行。

## 判定与恢复

- 领取、派单预检查和实际创建派单共用执行阻塞来源：人工执行安排、外部会话、派单会话、AI 执行和托管阶段。首次尚未领取的派单仍由既有派单冲突规则保护。
- 连接健康以节点心跳为准：节点心跳新鲜的 `idle` / `suspended` 会话且没有活跃回合或待处理命令，可按现有规则继续；会话自身的最后上报时间不参与连接判定（`idle` 会话上报间隔可长于观察窗口）。没有原生控制通道的完成跟踪记录不会仅因时间流逝变成在途执行。
- 活跃回合、运行或停滞状态、排队/送达中/送达未知的命令，以及未结束的人工/托管执行继续阻塞。
- 原生会话不可读（如 `unavailable`）、节点心跳过期或节点被撤销，以及仅有进展记录的旧执行，在没有实际活动或待处理命令时，允许有产品操作权的当前 Builder 或交付管理员逐条人工核实。中途失败、进展仍为 `working` 或没有旧轮次交付结束记录的情况同样适用。尚未建立会话的排队/启动派单仍须通过对应取消或停止操作处理。
- 人在原客户端或执行设备核实**该执行已经停止**后，在条目详情的执行记录填写依据、明确勾选并提交「核实停止」。这不是停止命令，不推断进程已退出，也不改变条目交付或验收结果。
- 实际运行、停滞或回合活跃、仍有未处理命令时，不提供确认入口。先在对应客户端处理实际活动或命令，不能强制重派。仅有 `working` 进展或执行记录本身不等于观察到进程活动。
- 人工/Agent 的执行安排与来源会话分别核实，不能只确认会话而遗漏仍在途的执行记录。每条执行显示工作范围，逐条确认；有明确会话关联的执行安排同时校验来源活动与命令，无法识别关联来源时保持阻塞。AI 执行和托管阶段仍由其既有生命周期处理。

## 权限与并发

`GET /api/v1/items/:itemKey/delivery` 返回 `executionBlockers`，包含具体来源、会话/执行标识、最后来源状态、进展状态、节点、同步时间、诊断及核实资格。

`POST /api/v1/items/:itemKey/execution-blockers/:blockerId/confirm-stopped` 仅接受已登录人工 Cookie，要求 `revision`、非空 `note` 和 `confirmedStopped: true`。不提供 MCP、节点或 Bearer 确认入口。归档/迁移条目只读。

提交在数据库事务中重新核对账号、项目、条目阶段和来源观察。来源的真实证据（状态、回合、命令、消息、活动代数）或条目变更会拒绝旧确认；仅观测时间戳移动不构成证据变化。每次确认只解除一个条目的一条历史执行；多条目会话、其他执行和其他账号的原生控制权限保持独立。Builder 交接也复用当前仍有效的条目级停止核实；一旦来源重新活动，交接仍须等待实际停止。

迁移 `202611031536` 新建停止核实记录及活动检查点，不补造任何历史停止结果。快照上报新活动、回合活跃、进展重新开始、插入新消息、创建命令或命令恢复送达均递增活动检查点并使旧确认失效；之后再次不可读也不能复用旧确认。重复的无活动不可用快照不撤销已经核实的停止结论。确认记录和失效时间保留，条目时间线记录人工、目标执行与依据，服务重启后仍有效。

验收打回/重开/恢复仅在确有在途执行时设置停止待确认；新领取清理旧处置提示。原有轮次凭据撤销规则保留，停止核实不能恢复旧凭据或证明新轮次交付。

## 共用界面与验证

- 服务端测试：真实旧案例、预检查/派单一致性、同一确认竞争、活跃回合、三种待处理命令、重新活动/命令/消息后的失效、节点离线/撤销/过期、多会话和多条目隔离、权限/归档/过期页面/Bearer 拒绝、旧凭据撤销、旧库升级及重启持久性。
- 浏览器测试：320px 触控和 1440px 桌面的明暗主题，长诊断不溢出、三档字号、手机横屏短高、明确勾选、草稿关闭保护、503 保留输入、提交期间禁用、成功局部刷新、新活动重新阻塞和过期确认拒绝。截图检查表单和按钮可达性。
- 生产案例只有在此修复发布后，才会出现上述核实入口；测试通过不等于已发布，也不能代用户确认生产执行停止。

发布范围为 `web`（Web/Server）。本地修复不包含 push、merge、生产发布或人工验收。

## AND-393 补齐的恢复链路

此前 AND-381 只覆盖已结束处理轮次，测试明确排除了中途失败；AND-391 的停止当前回合保留条目执行记录。因此“停止回合”与“重新领取”之间仍缺少旧执行核实出口。

按用户在 2026-11-04 批准的规则，`ready` / `inbox` 的中断条目也可由当前 Builder / 管理员记录人工停止依据。自动化复现一条人工领取记录和一条 `unavailable/working` 会话同时阻塞：确认会话后仍保留人工执行阻塞；逐条确认完毕，派单预检查、实际派单和新一轮领取才放行。条目状态、原会话进展和原执行记录均保持原样，不伪造完成结果。

迁移 `202611040657` 保留此前停止记录，拆开来源快照与进展更新的失效条件：重复无活动的不可用快照不会因旧进展仍为 `working` 撤销确认；新进展上报（包括再次上报同一状态）、活动、消息和命令仍使其失效。执行安排新增独立的核实审计和活动代数，执行状态、范围、关联会话或新报告更新后必须重新核实；关联来源的活动代数也纳入该执行的核实依据。新旧记录与失效证据均跨重启保留。

共用 `ExecutionStopNotice`、`ItemDeliveryPanel`、`Modal` 和原有样式；Web、Android WebView、macOS 内嵌页沿用同一入口，不增加原生协议。服务端测试覆盖完整新派单领取、多来源隔离、活动/三种命令阻断、同状态恢复上报、并发与过期确认；迁移测试覆盖旧库升级、已有审计保留及新确认重启；UI 补充 320px/1440px、明暗主题下两个 `working` 旧执行逐条核实，并保留原有草稿、请求、字号与可达性回归。发布范围仍为 `web`（Web/Server）。真实设备的进程及后台工具是否停止，仍只能由人在对应设备核实。

## AND-393 第二轮：连接健康以节点心跳为准

2026-11-05 验收打回暴露两处缺口：`sessionReason` 曾把会话最后上报时间（`agent_sessions.updated_at` / `native_synced_at`）纳入 90 秒连接窗口，而该时间戳被每次节点快照上报刷新，`idle` 会话的上报间隔实测可超过窗口——节点在线、会话 `idle`、无命令、无回合活动仍被间歇判为「连接未知」，阻塞随上报节奏抖动；同时人工确认的 `revision` 摘要含该时间戳，填写依据期间任何一次上报都会使提交被拒。验收打回不关闭旧派单，上一轮 `idle` 会话落入抖动判定，重新接手时断时续。

按用户在 2026-11-05 批准的规则：连接健康只看节点心跳（`nodes.last_seen_at` 在窗口内且节点未撤销）。心跳新鲜的 `idle` / `suspended` 派单会话与原生外部会话直接放行，不出现核实入口；仅节点心跳过期/缺失/被撤销，或会话状态本身不可读（`unavailable` 等）时，才保留 `connection_unknown` 与逐条人工核实。`revision` 摘要移除观测时间戳，与 `executionObservationKey` 的稳定证据字段对齐——仅时间戳移动不拒绝确认，状态、回合、命令、消息与活动代数变化仍拒绝并使既有确认失效。

回归覆盖：节点在线 + `idle` + 上报超窗的外部会话与派单会话均不阻塞；验收打回后节点在线时重新派单与新领取直接放行（本条目第二轮的真实场景）；节点离线/被撤销仍阻塞且可人工核实；确认表单读取与提交之间仅观测时间戳移动仍成功；活跃回合与待处理命令的原有保护不变。发布范围仍为 `web`（Web/Server）。
