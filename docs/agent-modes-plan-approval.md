# Agent 模式与方案批准

方案展示与批准入口遵守 [跨端协作与内容完整性](design-system.md#跨端协作与内容完整性)。原会话先完整呈现方案、验证与授权边界；网页审阅链接不能替代正文。现有原生确认不可用时的网页兜底仍按下文契约执行，不代表需要重新批准已有决定。

工作权限决定可以执行的操作；方案批准确认用户同意的方案和范围；领取记录任务归属；会话控制负责消息与运行状态。四者独立。

## 一次批准与执行

需要先审方案时，先调查、澄清、提出范围及验证目标。同一方案在原生客户端或 MissionGo 任一入口明确批准即可。已有明确实施指令持续有效，不因新回合、重启、权限变化或换入口要求第二次批准。只有方案或范围实质变化才重新审阅；工具权限批准不等于方案批准。

`claim_item` 恢复既有状态、归属、产品权限和幂等校验，不要求方案审批记录或节点模式回执。领取不授予实施、push、merge 或发布权限。原生 Plan 的退出仍遵守原生流程。

`request_plan_approval` 保留原会话身份及准确的范围、方案、验证目标；仅在尚未批准时发起一次人工确认。原生表单使用绑定账号、客户端和修订的签名往返。同一修订重复请求和 Web 重试均复用已保存决定。

原节点同步的待审方案先冻结范围。Codex 紧随其后的完整原生实施指令、Claude ExitPlanMode 的实际接受回执可以同步为该方案的原生批准；只同步决定，不启动第二个回合。不能把模式切换、AI 自述、普通提问答案或旧历史引用当作批准。未能可靠同步的来源保留真实记录状态，不要求用户为同一方案重复批准。

原生批准由原生回合继续；Web 批准在原通道可用且空闲时通过既有队列续办一次。运行中的会话自行继续，不排第二个回合。离线批准独立保存，连接恢复后仅在原上下文、范围与授权仍有效且来源未自行继续时补投递一次。新输入、停止、归档或上下文变化取消待续办；送达不明不自动重发。

## 原生语义与默认值

| 客户端 | 选项 | 无明确偏好时 |
| --- | --- | --- |
| Codex | 默认权限、自动审查、只读、完整访问权限 | 自动审查 |
| Claude Code | Default、Accept edits、Auto、Bypass permissions、Plan | 原生确认 Auto 可用时 Auto；确认不可用时 Bypass；未知时必须选择可用模式 |
| OpenCode | Plan、Build | Build |

Codex 完整访问目前受节点“受管工作区”策略禁止，界面禁用并说明原因。只读保持原生只读沙箱。方案审批不启动原生 Plan collaboration mode，也不覆盖所选沙箱；不会把 `plan` 继续当作权限选项。旧 Codex `plan` 按原有自动审查权限含义映射到 `auto`，原先等待批准的意图由统一批准流程保留。旧 OpenCode `default` 按原含义映射为 `build`。其他保存值不静默替换，失效值继续显示并要求处理。

Claude 的能力探测使用隔离的原生控制协议，不发模型请求、不运行用户 hooks。对当前配置与有限的原生模型目录逐项 `set_model`、`set_permission_mode`，只有返回的实际模式与请求相同才认定可用；明确拒绝为不可用，缺少回执或探测失败为未知。模型目录超过探测上限的选项保持未知。原生版本、供应商及组织策略通过实际回执体现，不按模型或渠道名称推断。实际会话切换模型后先重新校验模式，失败保留实际已生效字段并显示错误。

## Web 控制与运行状态

审批不取消已有会话关联，不禁用原本可用的回复、停止和设置能力。外部原生身份显式请求自动连接时，审批登记也沿用既有只读发现流程，无需先领取；尊重用户断开，只探测已启用集成的原 ID，不启动 CLI。不支持的来源能力如实提示。

保持既有健康判定：连续 10 分钟没有可确认进展提示“疑似卡住”，已知等待人工输入和非活动回合除外；超过 2 分钟未同步显示状态无法确认。两者均不自动中断、重发或释放执行占位。

AND-522：派单/项目会话与外部原生会话共用服务端健康归并。有效消息首次送达且此前已确认非活动时，以首次送达结算时间建立持久的本回合健康起点，避免旧回合的观测/进展时间让新回合立即误报；源 `observedAt`、`lastProgressAt` 不被回执伪造或刷新。没有后续源观测仍在两分钟后提示状态无法确认；同回合追加、重复/迟到回执和控制设置不续期。旧节点未提供观测时保持兼容。健康截止时间同步交给实时事件调度器，不依赖下一次业务轮询；真实无进展、失联、权限、停止和人工验收语义保持。

## 升级与回归

保留原有历史批准恢复审计。恢复证据失败不会变成领取门禁。迁移 202611051453 取消旧“等待实施模式后续办”意图，保留已排队命令及历史记录；新 Web 续办意图持久化并独立去重。Skill 5.43.0 和两端启动提示同步契约；旧会话需重读新版 Skill，内置提示和 Claude 原生回执需要更新节点。

回归覆盖领取与模式独立、原生/Web 一次批准、过期范围、重试、离线恢复、活动回合不重复启动、跨客户端凭据、原生历史拒绝和既有 Web 控制及健康规则。继续复用现有方案卡片、权限区、回复队列和设置组件，不增加工作方式选择。

### 处理中条目的显式 Agent 接手（AND-409）

人工在条目详情核实旧执行并指定原会话或新派单，保持处理中及 Builder。交接授权、方案决定、工作权限和实际领取分别生效。普通处理中条目不能直接重新领取；领取须消费有效交接授权并签发本轮凭据，不能因取消方案领取门禁绕过接手检查。接口与验证边界见 [AND-409 交接说明](and-409-agent-handoff.md)。

## Claude MCP 原生确认兼容

Claude 的 `ExitPlanMode` 使用 `can_use_tool`，MCP 的原生方案确认另用
`control_request.request.subtype=elicitation`。macOS 托管、外部桥接和 Linux 节点均须处理后者，
不能只转发普通工具授权，否则 MCP 调用会持续心跳却永远收不到人工结果。

- 现有 MissionGo 原生审批是空对象表单。复用会话问题卡及审批队列，保留服务名、完整确认内容、
  原请求 ID，展示批准／拒绝／取消；等待期间上报 `waitingForInput=true`，心跳不解除等待。
- 人工答复回传 `action=accept|decline|cancel`；批准同时带 `content={}`，不能使用工具权限的
  `behavior=allow|deny`。托管会话的答复绑定问题键，外部桥接仍只接受本机 `/answer <请求ID>`，
  普通 Web 文字不能代替外部审批。来源取消只撤销对应请求，迟到答复不能批准下一请求。
- 需要填写数据的表单、URL 确认和未知控制请求明确返回不支持错误并给出说明，让服务端走已有
  Web 交接；不能丢弃请求，也不能替用户填数据或批准。此兼容修复不更改方案修订和批准契约：
  同一修订复用既有批准，改写方案或验证目标仍产生不同修订。
- 协议及真实宿主子进程回归见 `ClaudeElicitationTests`、`ClaudeExternalBridgeTests` 和
  `apps/node/src/node.test.ts`；界面沿用 `AgentSessionQuestions`，验证见
  `tests/ui/agent-approval-visibility.audit.spec.ts`。

## 审批请求来源（AND-430）

自动待处理分类不提供方案批准权限，也不将普通回答包装为方案。正式审批来自明确登记的方案或原生 Codex/Claude 方案请求；OpenCode 的 plan 模式进度需明确登记后才可审批。正文缺失时返回 `content_unavailable`，前端禁止批准并允许重试。新的用户追问使旧待审请求不能批准，已登记正文和历史决定仍可阅读。以普通 Agent 消息承载的正式方案沿用来源消息位置，不因登记时间晚于正文而移到会话前后。

## 当前入口完整方案（AND-443）

三种客户端的 Skill、启动提示和 MCP 共同要求先展示完整方案、验证、风险及授权边界。原生确认不可用时，工具仍返回精确正文，网页 URL 仅补充导航；方案的一次续办规则保持；协作、恢复与托管决策可按 MCP 契约使用各自独立的可信原生人工确认。长正文可通过版本绑定的 get_review_content 读取，不用压缩摘要替代批准范围。只读查询不产生任何批准或执行事实。

## 文档方案审批（AND-452）

文档方案按统一规范展示核心摘要和固定版本 Markdown 链接，所有入口可读取完整原文；不再要求在消息里重复展开全部验证步骤。批准仍在原会话摘要下方，绑定 prepare_plan_document 的 documentId 与精确 plan，validation 为空。原生批准复用同一签名及版本核验，无法确认时交接同一 Web 审批，不重复要求有效人工决定。阅读文档不是批准，也不强制阅读。旧文本方案不自动改写。

原范围补修诊断记录引用 parentDocumentId，不建立新批准；实质方案变化仍需新版本审阅。后续归档、轮次和执行上下文参见 and-452-plan-documents.md。


## 固定文档文字批准与来源恢复（AND-515）

三种客户端的原节点最终答复可以承载已登记固定文档；不再要求文档答复必须使用原生 Plan 角色。服务端统一核验当前账号、原会话、固定文档/修订/摘要/范围及有效节点；展示的固定 plan 原文须完整一致，外部导航说明不扩大范围，多文档或冲突来源拒绝。只接受紧随展示的独立“批准”，不同于普通聊天、进度、条件句或工具授权。各适配器从真实协议保留最终完成标记及来源顺序；旧节点缺字段时显示限制。

实时认证报告核验可登记原决定；读取保持只读。历史补读只保存证据，显式 recover_plan_approval 或原会话的“核验原批准”使用同一核验器恢复。操作只属于原账号及原会话，不开放跨账号管理，不接受 Agent 自报批准。来源完整性、文档变更、撤权或冲突阻断时给出具体原因，不说用户拒绝。领域批准和 document_plan_decisions 审计同事务保存，保留原决定时间、消息 sourceId 与核验时间。重复恢复不重复批准、不排新回合、不取消在途命令。

两处会话入口共用 DocumentPlanRecovery、既有 agent-plan-record 与主题令牌；原文、位置、聊天草稿不被恢复操作改写。现有 Web/表单批准、归档精确批准门禁、范围变化失效及续办规则保持。回归：document-plan-approval.test.ts、各节点协议测试及 and-515-document-approval.audit.spec.ts。真实客户端与生产恢复需分别验证，测试或主线集成不代表已部署。
