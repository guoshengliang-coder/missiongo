# Agent 模式与方案批准（AND-400）

方案批准、客户端原生模式、工具权限批准分别记录。Bypass、Build、自动审查、完整访问及普通文字同意都不会生成方案批准。纯讨论/查询无需实施批准。

## 开发流程

1. Agent 读取条目和项目规则，完成诊断与澄清，提出方案及验证目标。
2. `request_plan_approval` 使用原派单或原外部会话身份，登记明确条目范围、方案和验证目标。`approvalMethod: web` 将精确版本交给会话中的批准按钮；`native`（默认）请求原生人工交互。它不领取、不写评论；首次外部会话按原身份建立待审批关联，批准和领取后沿用同一记录。
3. Web 登录用户批准，或原生客户端返回人工接受后，服务端保存批准人、来源、方案正文、验证目标、版本与条目内容边界。普通工具参数不能自报批准，技术权限请求也不提供这份授权。
4. 节点从第一轮应用明确选择的原生权限模式并回报实际生效结果；方案审批独立决定能否领取和实施。OpenCode/Claude 明确选择 Plan 时仍保持 Plan，需要明确选择实施模式。同一批准方案切换模式不重复批准。
5. 新方案取代旧请求，条目内容、返工或 Builder 交接边界变化使旧授权失效。旧版本、其他会话、其他账号、扩大的条目范围和未确认的原生模式不能用于领取。

批准、提问和投递继续复用现有会话、权限区、`Select`、`Modal` 与队列。派单不常驻展示固定开发流程，不增加“工作方式”或“沙箱范围”选项。

## 原生语义与默认值

| 客户端 | 选项 | 无明确偏好时 |
| --- | --- | --- |
| Codex | 默认权限、自动审查、只读、完整访问权限 | 自动审查 |
| Claude Code | Default、Accept edits、Auto、Bypass permissions、Plan | 原生确认 Auto 可用时 Auto；确认不可用时 Bypass；未知时必须选择可用模式 |
| OpenCode | Plan、Build | Build |

Codex 完整访问目前受节点“受管工作区”策略禁止，界面禁用并说明原因。只读保持原生只读沙箱。方案审批不启动原生 Plan collaboration mode，也不覆盖所选沙箱；不会把 `plan` 继续当作权限选项。旧 Codex `plan` 按原有自动审查权限含义映射到 `auto`，原先等待批准的意图由统一批准流程保留。旧 OpenCode `default` 按原含义映射为 `build`。其他保存值不静默替换，失效值继续显示并要求处理。

Claude 的能力探测使用隔离的原生控制协议，不发模型请求、不运行用户 hooks。对当前配置与有限的原生模型目录逐项 `set_model`、`set_permission_mode`，只有返回的实际模式与请求相同才认定可用；明确拒绝为不可用，缺少回执或探测失败为未知。模型目录超过探测上限的选项保持未知。原生版本、供应商及组织策略通过实际回执体现，不按模型或渠道名称推断。实际会话切换模型后先重新校验模式，失败保留实际已生效字段并显示错误。

## 兼容与验证边界

无关联条目的项目会话按明确选择的原生权限模式启动；Codex 自动审查保持 workspace-write，Claude Code 保留 Auto/Bypass 等选择，OpenCode 保留 Build，显式只读/Plan 也保持不变。讨论、需求登记和经确认的条目创建不要求先取得代码实施方案批准。普通项目开发仍须先调查并由用户明确批准方案；用户后来指定工作条目时，沿用原会话登记有范围的正式方案批准，未批准时由独立的方案记录阻止领取和实施，不切换原生模式。

节点设置中的旧 `planning` / `planApproved` 字段仅保留解码兼容，不再覆盖原生权限。所有会话发送所选 `mode` 与 `planning: false`；审批申请、批准和失效均不修改设置或递增设置修订版。数据库升级将旧强制阶段恢复为用户保存的模式并排队等待节点确认，保留模型、强度、实际模式、批准记录及其来源；不伪造生效或人工批准。需更新原生节点才能从首轮使用新语义。已有正式方案请求的会话仍受独立方案门禁约束。macOS 与 Linux 三个适配器共用该规则；外部接入会话保留原有来源权限边界。

节点 heartbeat 的 `planApprovalProtocol: 1` 表示本适配器支持独立方案批准协议与原生设置回执检查；未声明的旧节点不能接收新派单，排队任务也不会被旧节点领取，`permit-start` 再次校验，需升级。旧偏好与历史不删除，不虚构旧任务的批准记录。

注册了明确方案的外部会话可直接使用返回的 `reviewUrl`，无需原生回复连接。`approval` 关联只提供审批可见性，领取事务才把它升级为 `handling`；存量关联默认 `handling`。审批关联不产生执行凭据、开始处理日志或执行阻塞；普通会话登记、进展上报、执行授权恢复仍核对处理关联。

MCP SDK 2.0 的 2026-07-28 协议通过 `inputRequired` / `inputResponses` 完成人工确认，不调用旧推送式 `elicitInput`。`requestState` 使用 SDK 的 HMAC codec，绑定账号、OAuth 客户端和方法，并携带当前方案修订版；篡改、过期、跨客户端、缺失状态及方案边界变化均不能生成批准。密钥按进程共享（单进程部署），重启后未完成的原生往返需重新获取状态；已经保存的批准仍可复用。旧的无状态 2025 协议不能保留原生确认能力时返回同一方案的 Web 衔接入口。

Web 批准将领域决定与消息投递分开：已有命令响应保持兼容；不能投递时返回 `{approved:true, revision, continuationQueued:false}`。会话详情返回 `canApprovePlan` 与 `planApprovalState`，界面显示批准已保存及继续消息是否排队，不把批准当作已送达。显式外部方案的批准仍要求当前账号有操作/AI 权限且 Builder、修订、条目内容及范围有效；归档会话不提供批准。派单原有实施模式生效门禁保持。

`native_approval_unavailable` 表示衔接失败，不说明用户未同意；不得把它解释为拒绝并反复要求审阅同一方案。原生通用“执行此计划”界面、普通文字和权限切换不提供绑定方案的 MCP 回执，不能从聊天补造正式记录；需要完成上述可核验往返或 Web 决定。协议失败保留真实状态，不能用工具参数代替人工回答。外部会话仍保留原客户端支持的设置边界，不能借 Web 回复扩大原生权限。

必需发布产物为 Web/Server、macOS 客户端与 Linux CLI；无需重建 Android 壳或 Android SDK。交付时仍按实际 diff、发布覆盖门禁和公开制品核验，不能把测试通过当作已发布。

契约回归：`implementation-plan-gate.test.ts`、`implementation-plans.test.ts`、`plan-approval-routes.test.ts`、`AgentModeCapabilityTests.swift`、Linux native fixture 及既有会话恢复测试。界面回归覆盖派单、新会话、快捷设置、方案批准及窄屏“更多设置”。真实供应商账号、组织策略变化和真实 Linux/OpenCode 服务仍需在对应环境核验；模拟协议不能证明全部外部环境都可用。

原生接口参考：[Codex App Server](https://learn.chatgpt.com/docs/app-server)、[Claude Code 权限模式](https://code.claude.com/docs/en/permission-modes)、[OpenCode Agent](https://opencode.ai/v2/docs/agents)。

AND-405 回归：`external-plan-approval.test.ts` 使用真实 MCP HTTP 请求覆盖首次外部会话、离线 Web 批准、原生多轮确认、签名状态校验、重复与过期方案、权限和真实 tools/list 一致性；`plan-approval.audit.spec.ts` 覆盖无回复连接的批准及保存/投递结果。此修复只涉及 Web/Server 及公开 Skill，无需改原生节点源码。


### 升级前原生确认的正规恢复（AND-405 / Skill 5.39.0）

仅针对迁移 202611051005 之前已存在、尚未取得正式批准的 Codex 派单请求。迁移冻结原请求修订、原条目内容边界、原会话/节点，以及原节点同步的最新 `plan` 和紧接着逐字完整引用该方案的 `PLEASE IMPLEMENT THIS PLAN` 用户输入的消息 ID 与摘要。迁移本身不批准、不领取，不生成执行凭据；升级后新增请求或后来补入的消息不进入候选。

正常 `claim_item` 使用原账号/派单时，服务端重新检查产品操作与 AI 权限、当前 Builder、派单/节点未撤销、会话未归档、原请求修订与冻结范围、每个条目从未领取，及原生消息角色、顺序、全文、摘要均未变化。原生完整方案才是恢复后的正文，不能把 MCP 概述或普通“批准”聊天冒充用户接受的全文。更新请求在迁移后被取代、出现新原生方案或条目版本/范围变动时拒绝恢复。

恢复保存 `source: native` 的当前批准和独立审计：旧请求修订、恢复后的原生方案修订、源会话、源消息 ID/摘要、原生接受时间、恢复账号/OAuth 客户端与实际恢复时间。`get_item_plan_approvals` 的 `approval.recovery` 返回上述来源引用与两个时间；不伪造历史批准时间或处理日志。原派单批准在账号/派单级复用，正常领取凭据仍绑定实际调用的 OAuth 客户端，其他客户端不能使用或恢复该凭据。

批准恢复先独立持久化；若节点尚未确认原实施模式，领取继续被模式门禁拒绝，但不会回滚已恢复的真实决定。节点确认后沿用原领取参数/幂等键，正常生成本轮领取记录与凭据，再依次提交开发完成、发布待验证。幂等重试不重复恢复、不新建会话、不重复发送“批准”继续消息。现有 `recover_execution_authorization` 仍只恢复已经领取的凭据，不承担补领或审批恢复。

隔离回归 `legacy-plan-approval-recovery.test.ts` 覆盖真实数据库升级和重启、正常 MCP 领取至待验证、模式等待、重复请求、普通聊天/拒绝/取消/AI 伪装、消息篡改、新方案、新请求、范围变更、跨账号、客户端凭据隔离、只读权限、节点撤销、派单失效、Builder 和多条目边界。此次增量仅改 Web/Server 与公开 Skill，无原生节点源码变化。


### 历史恢复后的回合间续办（AND-405 / Skill 5.40.0）

真实 Codex 节点只在 idle 时应用实施模式。历史批准恢复发生在正在运行的原回合内时，正常领取保持模式门禁，并可返回 `{claimPending:true, continuationScheduled:true, statusChanged:false}`。这不是领取成功，没有执行凭据。服务端只为原账号、原 OAuth 客户端的真实历史恢复记录登记一次续办意图，不给普通未批准请求或其他客户端登记。

当前 Agent 应说明进展并结束本回合；原节点在回合间应用原选择的实施模式，向正常 snapshot 接口回报。服务端在真实 idle、模式已确认、无待答工具权限、无待发送或送达不明消息时，重核账号权限、Builder、原派单/节点、当前批准版本、原条目边界及仍待领取状态，再使用既有队列发出一条明确标注“系统续办，不是新的人工批准”的消息，继续原会话。无需重复批准或手工继续，不新建会话、不停止当前回合、不提前领取或自动推进卡片。

新的人类输入、停止、归档、取走条目、方案/范围/权限变化使等待中的意图失效。排队结果以 `approval.recovery.resume` 的 waiting/queued/cancelled、命令引用与时间核对；取消或送达不明不自动重发。服务重启保留意图及一次投递约束。续办后的 Agent 仍须核对合并、公开产物及发布凭据，正常领取并用本轮凭据提交开发完成/待验证。节点确认不等于执行交付，队列发送不等于验收。

原生历史回填或镜像可能改善消息 ID 和时间戳。续办对同一原生回合、相同全文作重复同步处理；新的回合或全文变化仍撤销意图，不从文本推断批准。UTC 迁移 202611051145 标记指纹格式，已有等待记录保留原 source 指纹语义，新记录使用稳定的回合/全文指纹。严格的历史批准来源校验与消息摘要不变。

取消的历史续办不会被节点上报自动复活。原账号/客户端重新调用原派单领取、当前用户输入已变化、批准修订/范围未变且从未排队时，可显式登记针对当前输入的新等待；原输入重试或已有命令引用不得重发。

### 处理中条目的显式 Agent 接手（AND-409）

人工在条目详情核实旧执行并指定原会话/新派单，保持处理中及 Builder。交接授权、当前方案批准、原生模式确认和实际领取分别生效。明确登记的派单方案也可离线保存批准，不能投递继续消息时明确返回 `continuationQueued: false`；不影响旧批准恢复机制。接口与验证边界见 [AND-409 交接说明](and-409-agent-handoff.md)。
