# 角色、条目状态权限与自动校正规则

日期：2026-11-02；产品：Mission GO；关联：AND-356 的后续需求。

性质：AND-357 附件确认规则的仓库留档；实施与验证见本文最后的核对记录。

## 1. 关键决定与角色范围

- 取消条目：系统管理员、项目管理员、提需者、当前 Builder 均可操作。
- 验收打回：也由这四类人操作，统一名称、统一事件和统计口径。
- 验收通过：仍限系统管理员、项目管理员、提需者。

| 角色 | 作用范围与职责 |
|---|---|
| 系统管理员 | 全局账号、权限、项目和异常治理 |
| 项目管理员 | 所属项目的成员授权、Builder 调配、条目治理、验收、归档与恢复 |
| 项目创建者 | 创建时默认成为项目管理员；后续管理权随当前角色调整，创建者身份保留为历史归属 |
| 提需者 | 对自己提出的条目作出需求与验收决定 |
| 当前 Builder | 对当前负责条目的执行、交付和责任转交负责 |
| 执行人 | 在明确安排的范围内执行工作、报告进展和提报结果 |
| 普通操作成员 | 录入、编辑、补充材料和协作；未分配的条目可主动认领 |
| 只读成员 | 查看有权访问的内容；若同时具备提需者等身份，仍可执行该身份允许的业务决定 |

角色可以叠加。提需者同时是 Builder 时，仍可验收自己的条目。Builder 责任转交后，旧 Builder 不再凭历史身份操作该条目。

## 2. 人工操作权限矩阵

下表中的“管理者”指系统管理员或所属项目的项目管理员。“需操作权”表示该身份本身不额外授予普通编辑、协作能力。

| 人工动作 | 管理者 | 提需者 | 当前 Builder | 执行人 | 普通操作成员 |
|---|---|---|---|---|---|
| 创建条目 | 可以 | 需操作权 | 需操作权 | 需操作权 | 可以 |
| 编辑草稿、待处理条目 | 可以 | 需操作权 | 需操作权 | 需操作权 | 可以 |
| 草稿提交待处理、待处理撤回草稿 | 可以 | 自己的条目 | — | — | 自己创建的条目 |
| 领取、开始处理 | 可分配、认领或接管 | 按执行资格 | 可以 | 明确授权后可以 | 仅未分配条目可主动认领 |
| 开工前暂缓 | 可以 | 自己的条目 | 可暂缓负责的待处理条目 | — | — |
| 处理中暂缓、释放回待处理 | 可以 | — | 可以 | 可报告阻塞 | — |
| 恢复暂缓 | 可以 | 原阶段为草稿或待处理 | 原阶段为待处理或处理中 | — | — |
| 提报开发完成 | 凭证据确认 | — | 凭证据提报 | 本轮授权范围内提报 | — |
| 提交待验证 | 发起核查或人工确认 | — | 提报交付证据 | 本轮授权范围内提报 | — |
| 开发完成退回待处理 | 可以 | — | 可以 | — | — |
| 验收通过 | 可以 | 自己的条目 | — | — | — |
| 验收打回 | 可以 | 自己的条目 | 当前负责的条目 | — | — |
| 取消尚未完成的条目 | 可以 | 自己的条目 | 当前负责的条目 | — | — |
| 恢复已取消条目 | 可以 | 自己的条目 | 当前负责的条目 | — | — |
| 重新打开已完成条目 | 可以 | 自己的条目 | — | — | — |
| 手动跨阶段纠偏 | 可以，必须说明原因并留痕 | — | — | — | — |
| 评论、补充材料 | 可以 | 需操作权 | 需操作权 | 需操作权 | 可以 |

- 提需者即使没有普通操作权限，只要账号有效、能够查看项目，仍可对自己的条目执行上表允许的业务决定。
- Builder、执行人候选必须具备完成相应工作的必要权限。人工 Builder 不强制要求 AI 权限；实际调用 AI 时再检查 AI 授权。
- 未分配条目认领成功后，建立 Builder 责任和本轮执行记录。已分配条目不得通过普通认领绕过责任转交。
- 验收打回统一记录操作人、操作时的相关身份、原因和处理轮次。Builder 主动返工也计入验收打回，不再另设“撤回交付”动作。

## 3. 正常状态流转

正常状态流转限定如下，操作人同时受上表约束。

| 当前状态 | 允许的正常去向 | 主要要求 |
|---|---|---|
| 草稿 | 待处理、暂缓、已取消 | 提交时补齐必要信息 |
| 待处理 | 草稿、处理中、暂缓、已取消 | 开工须确认责任与执行安排 |
| 处理中 | 开发完成、待处理、暂缓、已取消 | 开发完成有交付依据；释放、暂缓、取消须说明原因 |
| 开发完成 | 待验证、待处理、已取消 | 核实全部必要发布产物；无需发布走人工确认 |
| 待验证 | 已完成、待处理、已取消 | 回待处理统一记为验收打回，必须填写原因 |
| 暂缓 | 暂缓前状态、已取消 | 保存原阶段；恢复卡片与恢复执行分别处理 |
| 已完成 | 重新打开至待处理 | 必填原因，保留原验收记录，进入新一轮处理 |
| 已取消 | 恢复至草稿 | 必填原因，重新评估，不自动恢复原执行 |

取消、验收打回、重新打开、释放、暂缓、恢复和手动纠偏都需要原因，可附图片或文件。已完成条目不能直接取消。

## 4. 需求修改与验收版本

| 修改时机 | 规则 |
|---|---|
| 草稿、待处理 | 按普通操作权限编辑 |
| 处理中、开发完成 | 实质性需求变更由 Builder 或管理者确认，产生新内容版本，旧交付证据重新核对 |
| 待验证 | 实质性修改前先验收打回，再重新提交验证 |
| 已完成 | 实质性修改前先重新打开或建立新修订，不能继续沿用原验收结论 |
| 所有阶段 | 评论、补充说明及不影响验收的元信息，可按权限维护 |

## 5. 自动校正规则

现有“依据代码和发布事实自动校正状态”的能力保留。自动校正必须关联本条目的当前处理轮次、需求版本和交付依据，不能仅凭最新主线存在相关代码来推断状态。

| 场景 | 自动校正规则 |
|---|---|
| 本轮代码已集成，卡片仍在草稿、待处理或处理中 | 可自动校正为开发完成；必须已有本轮处理记录和已登记的交付依据 |
| 本轮全部必要产物已核实发布 | 可自动推进至待验证 |
| 明确无需发布 | 不伪造发布事实；由管理者或当前 Builder 通过有记录的人工确认路径安排验证 |
| 人工验收打回，包括 Builder 打回 | 旧交付轮次立即失效，旧证据不能再次把条目推回待验证 |
| 人工暂缓 | 保持暂缓，交付事实可以继续记录；恢复后再核查是否需要推进 |
| 人工取消 | 保持已取消，不自动恢复 |
| 人工重新打开 | 旧轮次证据失效，重新建立处理与交付关联 |
| 人工验收通过 | 保持已完成，系统不能代替人工验收或自动重新打开 |
| 仅整理卡片位置，没有表达打回、暂缓、取消等业务决定 | 仍允许按本轮有效证据自动校正，界面说明校正原因 |
| 需求范围或 Builder 发生变化 | 重新核对当前轮次、授权和交付关联，旧结果不得直接沿用 |

例如，版本 A 已发布后条目进入待验证，随后被验收打回。即使版本 A 仍在线，系统也不能自动恢复待验证；需要重新处理并核实交付依据。

恢复暂缓通常延续原处理轮次；返工、重开、取消后的恢复不直接复用旧执行授权和旧交付结论。异步检查写回前，必须重新检查当前状态、轮次、内容版本和最新人工决定，防止旧结果覆盖刚发生的打回或取消。

## 6. AI 与机器身份

| 主体 | 允许范围 | 禁止范围 |
|---|---|---|
| AI Agent | 在用户指派范围内创建、领取、执行和提报交付；状态写入统一检查操作权、AI 权限和本轮执行授权 | 验收通过、验收打回、取消、重开、强制纠偏 |
| 交付核查系统 | 根据当前有效证据推进开发完成、待验证，并执行上述自动校正 | 用旧证据覆盖人工业务决定；把执行结束当作验收通过 |
| SDK | 创建反馈条目 | 推进已有条目的状态 |
| 运维凭据 | 明确的诊断、备份与维护操作，记录机器身份 | 冒充人工账号作业务决策 |

## 7. 统一执行机制

- 单条、批量、HTTP、MCP、节点共用同一套判定。返回可用动作和禁止原因，关闭旧入口的校验例外。
- 每次写入重新检查权限。账号停用、撤权、责任转交即时影响后续操作；批量逐条判断并报告结果。
- 状态操作绑定版本并支持幂等重试。旧页面不能验收新一轮成果，网络重试不能重复产生业务决定。
- 保留完整审计。记录操作人、当时身份、授权依据、前后状态、原因、内容版本、处理轮次及交付证据。
- 业务状态与执行状态独立。取消或暂缓条目时明确在途执行如何处置；无法确认停止时显示执行仍在运行或停止待确认，并防止启动冲突执行。
- 归档项目默认只读。保留管理者恢复及必要权限修复入口；恢复后才能继续新建和处理条目。
- 通知有明确接收人。验收打回、取消、重开通知提需者和当前 Builder；提需者缺失、停用或不可访问时，由项目管理员承接。
- AI 范围显式配置。使用“全部项目／指定项目／禁止”三种模式，清空授权不自动变成全部开放。

本稿确认后，可作为后续实现、迁移和回归验收的统一依据。


## 8. 实施核对

规则入口：`services/server/src/item-policy.ts`。身份取当前有效账号、项目角色、不可变创建来源和当前 Builder，单条、批量、MCP 和交付写入复用判定。HTTP 返回 `transitionDecisions`（含禁止标识），MCP 上下文返回执行策略。正常的验收通过／打回、重开和恢复由服务端归一化，不依赖客户端填写旧动作名称。

- **项目角色**：新建项目默认授予创建者项目管理员；迁移保留现有创建者的管理能力。随后按当前管理员关系判断管理权，历史创建者字段不再作为永久管理权。项目管理员具备本项目治理、成员授权和普通操作能力，AI 权限另行检查。
- **执行主体**：人工 Builder 候选需要当前操作权；实际 Agent 执行再查 AI 权限。执行人必须有操作权，关联 Agent 还需 AI 权限。领取建立责任与执行记录；转交永久撤销旧凭据，已撤销的执行可报告实际结束，不能重新启动。
- **命令版本**：人工状态写入必须提交观察到的 `expectedRevision` 和稳定幂等键；批量逐条携带版本。前端保留同一次命令、上传和批量决定的重试键。人工交付确认同时绑定条目版本与交付关联版本。
- **内容版本**：标题、需求正文、结构化要求、类型、模块范围和平台属于实质性范围。实质性变更冻结于待验证、已完成、已取消；处理中、开发完成和暂缓阶段由当前 Builder 或管理者确认。版本快照及变更前后值持久化；优先级、补充环境信息等元信息可按操作权维护。
- **处理与交付轮次**：普通卡片整理保留原执行关联；暂缓恢复不新建轮次、不自动恢复执行。打回、取消、重开撤销旧执行授权；范围变化生成新的交付关联版本。开发完成后的范围变化也须重新核实开发完成，不能直接复用旧结论提交待验证。
- **交付事实**：状态校正使用事务重新核对状态、轮次和最新内容；暂缓可记录事实，恢复后再核查。发布来源记录真实产物提交，不用合并提交冒充发布来源。人工将未知范围安排为无需发布验证时，说明成为明确无需发布依据并留痕。
- **执行处置**：有在途执行的暂缓／取消必须明确处置。停止待确认只记录待核实事实，不表示已经向任意原生会话发出停止命令；源会话仍显示实际运行状态。新执行在旧执行未结束或状态未知时被阻止，仍可在原执行记录报告实际结束。原生停止与 Builder 转交沿用已有停止确认协议。人工领取责任记录随明确的 Builder 转交标记交接；具体执行人工作和原生进程仍保留真实状态。
- **归档**：条目、协作、SDK 反馈写入和新执行均受项目归档限制；管理者可恢复项目或修复授权。状态与执行终态保持独立。
- **审计与通知**：状态事件保存账号、当时身份、授权依据、前后状态、原因、内容版本、轮次和证据。项目角色、账号和项目权限配置变更也保存前后记录。打回、取消、重开通知提需者及当前 Builder，提需者无效时用当前项目管理员兜底；无可用接收人记录跳过原因。队列保存不等于通知已送达。
- **AI 范围**：显式保存 `all`／`selected`／`none`。迁移保持原有效范围；更新为空的指定清单不自动变成全部。项目侧授权仅修改本项目的记录，不隐式改动账号全局 AI 范围。MCP 交付与交接工具必须带当前领取凭据，没有首次 Builder 转交前的免凭据例外。公开 Skill 同步为 5.31.0。

自动化定位：`item-policy.test.ts` 覆盖角色矩阵、真实 HTTP/MCP、撤权、重试、轮次、旧页面、通知与执行冲突；`storage/item-policy-migration.test.ts` 覆盖有数据升级、有效／过期凭据和重复启动；既有交付、发布、转交、统计、附件与权限测试继续回归。界面覆盖列表／详情／批量、原因附件、状态检查、窄屏／桌面与明暗主题；新控件复用 Select、Modal 和现有草稿保护。

合并与正式发布须另有实际集成、CI 和发布凭据。真实钉钉送达、真实原生进程停止及终端浏览器效果按对应环境验收，不由测试夹具代替。
