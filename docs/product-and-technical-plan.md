> **From idea to shipped.**

## 1. 文档目的

本文档用于固定首版产品范围、核心概念、业务流程、技术架构、安全边界和分阶段实施顺序。

本文档通过评审后，才进入代码实现。后续新增需求默认进入后续阶段，除非它会阻塞首版核心闭环。

## 2. 产品概述

MissionGo 是一套面向独立开发者的个人自托管工作事项与 AI 执行工具，解决以下问题：

- 随时记录 Idea、Requirement、Bug、Task 和 Note。
- 从正在开发的 Android 或 macOS App 内直接提交反馈，并自动携带运行现场。
- 在 Android 管理 App 或 Web 端统一查看、搜索、补充和验收任务。
- 让 Codex、Claude Code、Hermes 等 AI 工具通过 MCP 按任务编号读取完整上下文。
- 通过 Skill 教会 AI 分析、领取、修改代码、运行测试和回写处理报告。
- 保留完整的人工与 AI 操作时间线，减少重复解释和复制粘贴。

核心闭环：

```text
发现问题或产生想法
→ 快速提交
→ AI 按编号读取完整上下文
→ AI 分析或处理代码
→ 回写结论、修改和测试证据
→ 人工回归验收
→ 完成或重新打开
```

## 3. 已确认的产品决策

| 事项 | 首版决策 |
|---|---|
| 使用对象 | 个人使用、单用户、不开启公开注册 |
| 产品数量 | 支持多个产品 |
| 顶层概念 | 使用“产品”，避免与代码项目、Git 仓库混淆 |
| 管理端 | Android 管理 App + 响应式 Web/H5 |
| Android 管理 App | Web 技术为核心，增加 Android 原生外壳与原生桥接 |
| Android 分发 | 自行安装 APK，不考虑应用市场 |
| 反馈 SDK | 首版支持 Android 和 Swift macOS |
| iOS | 首版不做；未来复用 Web 界面并增加原生外壳或 SDK |
| SDK 表单 | 原生 SDK 采集上下文，共用 H5 表单完成编辑与提交 |
| AI 接入 | Skill 负责工作流，MCP 提供实时数据与受控操作 |
| 数据库权限 | AI 不接触 SQL，不提供通用 SQL 工具 |
| AI 启动方式 | 首版按需启动，不做定时或无人值守调度 |
| AI 处理权限 | 可领取、修改、编译、测试并生成本地 commit |
| Git 远程操作 | 默认不自动 push，不自动合并主分支 |
| 最终关闭权限 | AI 推进到“已处理，待验证”；人工验证后关闭 |
| AI 结果 | 分析、处理结论、测试证据和验收结果追加到任务时间线 |
| 崩溃采集 | 首版不做自动崩溃上报 |
| 数据存储 | 首版优先 SQLite + 服务器本地附件目录 |
| 后续调度 | 可扩展为管理端点击后推送到 Mac mini 或服务器 AI 节点 |
| 开源安全 | 域名、端口、Token、密码、签名密钥和本地路径不得提交 GitHub |

## 4. 首版目标与非目标

### 4.1 首版目标

首版必须打通以下纵向流程：

1. 在 Web、Android 管理 App 或反馈 SDK 中创建任务。
2. 任务可以携带描述、环境信息、日志、截图和录屏等附件。
3. 用户在代码仓库内向 AI 指定一个任务编号。
4. AI 通过 MCP 获取完整任务上下文。
5. AI 可以只分析，也可以领取后修改代码并运行验证。
6. AI 将结构化结论和证据回写任务。
7. 用户在管理端进行人工验收，通过后关闭；失败则重新进入待处理。

### 4.2 首版非目标

以下内容明确不进入首版：

- 多用户、团队、组织、角色协作。
- iOS 管理 App 和 iOS 反馈 SDK。
- Google Play 或其他应用市场发布。
- 自动崩溃采集和崩溃聚合分析。
- 定时唤醒 AI、无人值守队列或常驻调度器。
- 从管理端主动启动 Mac mini 或服务器上的 AI。
- 自动合并主分支。
- 默认自动推送 Git 远程分支。
- PostgreSQL、多实例部署和 S3 对象存储。
- 看板、Sprint、工时、甘特图等传统项目管理功能。
- 面向公众的 SaaS 服务。

## 5. 核心概念与归集方式

### 5.1 概念定义

- **产品（Product）**：用户认知中的完整应用，例如 Hermes Go。
- **组件（Component）**：可单独构建、发布或修改的技术单元，例如 Android 客户端、macOS 客户端、服务端、公共核心；组件可以通过父子关系组织成多层结构。
- **功能模块（Area）**：产品内的业务区域，例如登录、同步、AI 对话、设置。功能模块保持扁平，不做无限层级嵌套。
- **代码仓库（Repository）**：代码实际存放位置。一个产品可以关联一个或多个仓库。
- **工作事项（Work Item）**：统一承载 Idea、Requirement、Bug、Task 或 Note，并拥有稳定编号。
- **执行记录（Execution Run）**：某个 AI 对任务进行的一次分析、处理或验证尝试。
- **来源组件（Source Component）**：反馈被发现或提交的平台组件。
- **影响组件（Affected Components）**：经人工或 AI 分析后，实际需要修改或验证的组件集合。

### 5.2 Hermes Go 示例

```text
产品：Hermes Go
├── 组件
│   ├── Android 客户端
│   ├── macOS 客户端
│   ├── 公共核心/协议
│   └── 服务端（如有）
├── 功能模块
│   ├── 登录
│   ├── 数据同步
│   ├── AI 对话
│   └── 设置
└── 代码仓库
    └── hermes-go
        ├── android/
        ├── macos/
        └── shared/
```

Android 和 macOS 不作为两个独立产品。任务属于 Hermes Go，并分别记录来源组件与影响组件。

### 5.3 跨组件任务

一条任务始终保留一个主编号，例如 `HG-128`。如果问题影响多个组件，可以在该任务下创建多个执行项：

```text
HG-128
├── Android 修改与测试
├── macOS 修改与测试
└── 公共协议修改与测试
```

## 6. 用户场景

### 6.1 快速记录想法

用户在 Android 管理 App 中快速输入标题和简短描述，选择产品后保存。其余字段可以后续补充。

### 6.2 从开发中的 App 提交 Bug

用户在 Android 或 macOS App 中打开反馈入口。SDK 自动采集版本、构建号、系统、组件和最近日志，创建临时草稿，再打开共用 H5 表单。用户补充描述和附件后提交。

### 6.3 指定 AI 分析任务

用户在正确的代码仓库中输入：

```text
分析任务 HG-128，先不要修改代码。
```

AI 获取任务和附件、检查相关代码并回写分析结论，但不领取任务、不修改文件、不改变任务状态。

### 6.4 指定 AI 处理任务

用户输入：

```text
处理任务 HG-128。
```

AI 领取任务、建立隔离工作区、修改代码、运行构建与测试、创建本地 commit、回写处理报告，并将任务推进到“已处理，待验证”。

### 6.5 连续处理队列

用户输入：

```text
处理当前产品的反馈队列。
```

AI 按优先级和创建时间连续领取任务，直到队列为空、用户中止或遇到需要人工介入的任务。

### 6.6 人工验收

用户在 Android 管理 App 或 Web 中查看修改说明和验证步骤。验收通过后关闭任务；失败则填写原因并重新打开。

## 7. 功能需求

### 7.1 产品配置

- 创建、编辑、停用产品。
- 设置产品简称，用于生成任务编号，例如 `HG-128`。
- 管理组件、功能模块和代码仓库逻辑信息。
- 配置 AI 是否可分析、领取、修改、提交和自动 push。
- 首版默认禁止自动 push 和自动合并。

### 7.2 任务管理

首版工作事项类型：

- Idea
- Requirement
- Bug
- Task
- Note

首版优先级：

- 紧急
- 高
- 普通
- 低

任务核心字段：

- 稳定任务编号
- 标题、详细描述
- 类型、优先级、状态
- 所属产品
- 来源组件
- 一个或多个影响组件
- 功能模块、标签
- 复现步骤
- 期望结果、实际结果
- App 版本、构建号、Git commit/build 标识
- 系统和设备信息
- 自定义上下文
- 截图、录屏、文件和日志附件
- 创建时间、更新时间
- 评论、事件和 AI 执行时间线

### 7.3 搜索与筛选

- 按任务编号直接查找。
- 按标题、描述和备注全文搜索。
- 按产品、组件、模块、类型、优先级、状态筛选。
- 默认提供“待我处理”“待我验证”“AI 正在处理”“最近更新”等快捷视图。

### 7.4 评论与时间线

原始反馈不被 AI 覆盖。以下内容全部以时间线事件追加：

- 人工补充说明
- AI 分析结论
- AI 关键进度
- 等待人工的问题
- AI 处理报告
- 自动验证结果
- 人工验收通过或失败
- 状态变化、领取、释放和租约过期

系统不保存或展示模型的内部思维过程，只保存可复核的结论、操作、证据和测试结果。

### 7.5 附件和日志

- 附件元数据保存在数据库，文件保存在受控附件目录。
- 附件不可使用永久公开 URL。
- MCP 通过受控资源或短期访问地址提供附件。
- 支持配置单文件大小、单任务总大小、允许类型和保留期限。
- 日志需要截断、分页和脱敏。
- 首版保证截图可供 AI 使用；录屏允许上传和人工查看，AI 对视频内容的理解按客户端能力尽力而为。

## 8. 状态模型

### 8.1 工作事项状态

```text
Inbox → Ready
          ↓ AI claim
      In Progress ───→ On Hold
          ↓                │ resume
      Pending Verification ←┘
          ├── verification passed → Done
          └── verification failed → Ready
```

另设 `Cancelled`，由人工使用。

### 8.2 状态规则

- `Analyze` 不改变工作事项状态。
- `Process` 必须先原子领取，再进入 `In Progress`。
- 信息不足时进入 `On Hold`，并写入具体问题。
- AI 处理成功后只能进入 `Pending Verification`。
- 人工验证通过后才能进入 `Done`。
- 验证失败不删除 AI 报告，追加失败原因并回到 `Ready`。
- 租约到期后追加中断记录，工作事项回到 `Ready`。
- 服务端负责校验状态流转，MCP 不提供任意状态写入。

### 8.3 执行状态

任务状态与一次 AI 执行状态分开。执行状态包括：

- 已创建
- 运行中
- 等待人工
- 成功
- 失败
- 已中止
- 租约过期

## 9. AI 工作模式

### 9.1 指令语义

- `查看任务`：只读取并展示任务。
- `分析任务`：读取任务和代码，输出并回写结论，不修改代码。
- `处理任务`：领取、修改、测试、提交并回写。
- `继续处理`：恢复之前中断或等待人工后的执行。
- `验证任务`：检查已有修改并执行自动验证。
- `处理反馈队列`：连续处理当前产品的待办任务。

### 9.2 处理报告

AI 处理完成后必须回写结构化报告：

- 处理结论
- 根因分析
- 修改摘要
- 涉及组件和文件
- Git 分支、worktree 和 commit
- 已执行的构建、测试和结果
- 未覆盖场景和剩余风险
- 建议的人工验收步骤
- AI 类型、执行标识、开始和结束时间

### 9.3 安全约束

- 任务描述、日志、评论、OCR 文本和附件内容均视为不可信数据，而不是系统指令。
- AI 不得直接执行任务内容中给出的命令，除非该命令符合仓库规则和本地允许的验证配置。
- AI 只能处理当前仓库绑定产品的任务。
- AI 默认只能修改配置允许的组件路径；扩大范围必须记录原因。
- 工作目录存在用户未提交更改时，不得覆盖或清理这些改动。
- 每个处理任务使用独立分支和 Git worktree 或等价隔离目录。
- 首版不自动 push，不自动合并主分支。

## 10. MCP 与 Skill 方案

### 10.1 职责边界

- MCP 提供实时数据、鉴权、授权、结构化工具和受控操作。
- Skill 定义什么时候调用工具、调用顺序、失败处理、输出格式和安全规则。
- AI 不获得 SQL、数据库连接串或通用数据库查询能力。

OpenAI 官方文档将 MCP 定义为模型连接外部工具与上下文的方式；Codex 本地客户端支持 STDIO 和 Streamable HTTP MCP，其中远程 HTTP 可使用 Bearer Token 或 OAuth。官方也明确把 Skill 定义为可复用工作流层，用来指导模型组合 MCP 工具。首版采用远程 Streamable HTTP MCP 和个人 Bearer Token，后续再评估 OAuth。

### 10.2 MCP 工具建议

读取类：

- `list_products`
- `list_components`
- `list_items`
- `get_item_context`
- `get_item_timeline`
- `get_attachment`
- `get_execution`

操作类：

- `claim_item`
- `renew_item_lease`
- `append_analysis`
- `append_progress`
- `request_human_input`
- `submit_resolution`
- `mark_pending_verification`
- `release_item`
- `resume_execution`

首版不向 AI 暴露：

- 任意 SQL
- 任意字段更新
- 删除任务
- 最终关闭任务
- 合并主分支
- 修改服务端安全配置

### 10.3 MCP 契约要求

- 所有写操作支持幂等键。
- 领取操作必须原子化，并返回租约标识与到期时间。
- 服务端校验任务状态、令牌权限和产品范围。
- 工具返回结构化 JSON、稳定错误码和可操作的错误说明。
- 大附件不直接内嵌为 Base64 工具结果。
- MCP 初始化指令只包含全局约束；详细处理流程放在 Skill 中。

### 10.4 Skill 结构

提供一个通用工作流核心，并针对不同客户端提供薄适配：

```text
feedback-skill/
├── SKILL.md
├── references/
│   ├── task-workflow.md
│   ├── status-rules.md
│   └── security-rules.md
└── scripts/（仅在确有必要时）
```

客户端适配目标：

- Codex
- Claude Code
- Hermes

不同客户端是否完整支持相同的 Skill 发现与调用方式，需要分别做契约测试；MCP 工具协议保持一致。

## 11. 系统架构

### 11.1 首版逻辑架构

```text
Android 管理 App（Web 核心 + 原生桥接）
Web/H5 管理端
Android 反馈 SDK
macOS Swift 反馈 SDK
            │
            ▼
      HTTPS API / H5
            │
┌───────────▼──────────────────────┐
│ 模块化单体服务                   │
│ - 认证与令牌                     │
│ - 产品/组件/模块                 │
│ - 任务、时间线、执行记录         │
│ - 附件与草稿                     │
│ - REST API                       │
│ - Streamable HTTP MCP            │
└───────────┬──────────────────────┘
            │
      SQLite + 附件目录
            ▲
            │ MCP
 Codex / Claude Code / Hermes
            │
       本地代码仓库与测试环境
```

### 11.2 架构原则

- 首版使用模块化单体，不拆微服务。
- Web、Android 外壳和 H5 表单复用同一套前端组件与 API 客户端。
- REST API 与 MCP 共用领域服务，避免两套状态规则。
- 数据库不直接暴露给客户端或 AI。
- 附件存储通过接口抽象，未来可替换为 S3 兼容对象存储。
- 数据访问层通过迁移机制管理，未来可以增加 PostgreSQL 适配。

## 12. 推荐技术方向

以下为技术方案基线，具体版本在实施阶段锁定：

- **代码组织**：monorepo。
- **共享 Web 前端**：TypeScript 响应式 Web/PWA。
- **Android 管理 App**：Capacitor 原生容器 + 自定义 Android/Kotlin 桥接。
- **服务端**：TypeScript 模块化单体，提供 REST API 和 Streamable HTTP MCP。
- **首版数据库**：SQLite。
- **附件存储**：服务器本地目录，通过统一存储接口访问。
- **Android 反馈 SDK**：Kotlin Library/AAR。
- **macOS 反馈 SDK**：Swift Package，兼容 SwiftUI 与 AppKit。
- **管理端认证**：单管理员账号和会话。
- **MCP 认证**：可撤销、可限定产品和权限范围的 Bearer Token。

Capacitor 的官方定位是以 Web 为核心、通过插件访问 Android/iOS 原生能力，符合“共享 Web + Android 原生外壳 + 未来复用到 iOS”的方向。Swift Package Manager 可以将 macOS SDK 作为库产品供现有 Swift 工程依赖。

## 14. 数据模型草案

首版核心实体：

| 实体 | 作用 |
|---|---|
| `users` | 单管理员账号，为未来扩展保留结构 |
| `products` | 产品与编号前缀 |
| `components` | Android、macOS、服务端、公共核心等组件 |
| `areas` | 登录、同步等功能模块 |
| `repositories` | 仓库逻辑信息，不保存本地绝对路径和 Git 凭据 |
| `work_items` | 工作事项主体和当前状态 |
| `work_item_affected_components` | 工作事项与影响组件的多对多关系 |
| `work_item_events` | 不可变状态和审计事件 |
| `comments` | 人工与 AI 可读备注 |
| `attachments` | 附件元数据和受控存储位置 |
| `execution_runs` | 每一次分析、处理或验证执行 |
| `work_item_leases` | AI 领取租约 |
| `access_tokens` | SDK、MCP 等令牌摘要和权限范围 |
| `feedback_drafts` | SDK 创建的短期反馈草稿 |

未来管理端主动派发 AI 时增加：

- `agent_nodes`
- `dispatch_requests`
- `node_capabilities`

`execution_runs` 首版即保留 `trigger_source`、`agent_kind` 和可空 `node_id`，为后续扩展留出兼容空间。

## 15. 反馈 SDK 设计

### 15.1 共用提交流程

```text
原生 SDK 采集上下文
→ 服务端创建短期草稿
→ SDK 使用一次性或短期凭证打开内嵌 H5
→ 用户补充描述、预览日志、添加或删除附件
→ 正式提交
```

敏感内容不得通过 URL 查询参数传递。

### 15.2 Android SDK

职责：

- 初始化产品和组件标识。
- 提供打开反馈入口的 API。
- 采集 App 版本、构建号、Android 版本和设备基础信息。
- 提供日志与操作轨迹环形缓冲区。
- 创建草稿并打开 H5。
- 支持图片、录屏和文件选择。
- 网络不可用时保存本地草稿。

### 15.3 macOS SDK

以 Swift Package 形式提供，兼容 SwiftUI 和 AppKit：

- 采集 App 版本、构建号、macOS 版本和设备架构。
- 提供 Swift API 写入业务上下文、日志和操作轨迹。
- 通过内嵌 Web 视图打开共用 H5。
- 支持当前 App 窗口截图或人工选择附件。
- 不默认采集整机系统日志。
- 不要求自动屏幕录制权限。

### 15.4 日志原则

- SDK 维护有限长度的内存环形缓冲区。
- 宿主 App 主动写入日志和 breadcrumb。
- 提交前允许用户预览和移除日志。
- 支持字段名、正则和长度规则脱敏。
- 禁止默认采集密码、Token、Cookie、完整请求头和个人敏感信息。

## 16. 管理端设计

### 16.1 Web/H5

首版页面：

- 登录
- 首页概览
- 产品列表与配置
- 任务列表、搜索和筛选
- 任务详情与时间线
- 新建与编辑任务
- AI 执行记录
- 人工验证
- SDK/MCP Token 管理
- 系统备份与导出入口

### 16.2 Android 管理 App

复用 Web 主界面，原生层提供：

- 系统分享目标，将图片、文本或链接快速创建为任务草稿。
- 相册、相机、文件与录屏附件访问。
- 本地草稿和失败重试。

- 后续通知能力的桥接接口。

首版通过 APK 自行安装，不实现应用商店相关流程。首版可以手动检查和下载新版本；自动更新留待后续。

## 17. 本地 AI 与仓库映射

服务端只保存仓库逻辑标识，不保存用户 Mac 上的绝对路径。每台开发机器维护自己的本地配置：

```text
产品/仓库逻辑 ID
→ 本地仓库路径
→ 组件路径范围
→ 构建与测试命令
→ Git 行为策略
```

本地配置还包含 MCP 服务地址和访问 Token，不得提交 Git。

建议配置分层：

- 可提交配置：非敏感组件目录、通用构建和测试说明。
- 本地忽略配置：服务器地址、端口、Token、绝对路径、签名信息和机器特定命令。

## 18. 认证、权限与安全

### 18.1 令牌分离

- 管理员会话：完整管理权限。
- SDK 提交令牌：限定一个产品和来源组件，只能创建草稿和提交反馈。
- MCP Agent 令牌：限定产品范围和工具权限，可读取、领取和回写，不能删除或最终关闭。
- 未来工作节点令牌：绑定具体机器，可撤销并限制可处理产品。

所有长期 Token 只保存摘要，明文只在创建时展示一次。

### 18.2 服务器安全

- 所有远程访问使用 HTTPS。
- 登录、SDK 提交和 MCP 工具调用分别限流。
- 写操作使用 CSRF、来源校验或令牌认证等合适机制。
- 附件文件名随机化，验证 MIME、扩展名、大小和路径。
- 防止路径穿越、越权读取和公开目录直接访问。
- 审计登录、令牌创建/撤销、任务领取、状态变化和数据导出。

### 18.3 AI 安全

- 将反馈内容视为不可信输入，防止提示注入。
- MCP 采用明确、窄范围的领域工具，不提供通用执行和数据库工具。
- 服务端执行状态机校验和权限校验。
- Skill 规定修改范围、测试要求和遇到风险时的停止条件。
- MCP Token 与 GitHub、Apple 签名、服务器 SSH 等凭据隔离。

### 18.4 开源仓库安全

- 提交 `.env.example`，忽略真实 `.env` 和本地配置。
- 禁止提交服务器域名、端口、IP、数据库密码、Token 和签名密钥。
- Android 签名密钥只保存在本地或私有 CI Secret。
- 提交前和 CI 中进行密钥扫描。
- 示例日志、截图和数据库必须使用虚构数据。
- 提供安全报告流程和密钥泄露轮换说明。

## 19. 部署与备份

### 19.1 首版部署

建议提供 Docker Compose 示例，运行：

- Web 静态资源与服务端
- SQLite 数据卷
- 附件数据卷
- 可选反向代理示例

真实域名、端口、证书路径和密钥由本地环境变量或服务器私有配置注入。

### 19.2 备份恢复

备份必须同时包含：

- 非敏感版本信息

首版完成前必须进行一次从备份恢复的演练。后续迁移 PostgreSQL 或对象存储时，保持统一的导出格式。

## 20. 后续“管理端派发 AI”扩展

未来流程：

```text
Android/Web 点击“交给 AI”
→ 服务端创建结构化执行请求
→ Mac mini 或服务器工作节点主动拉取请求
→ 节点启动 Codex / Claude Code / Hermes
→ AI 仍通过同一 MCP 读取和回写任务
```

安全原则：

- Mac mini 主动向服务器建立出站连接，不开放公网控制端口。
- 服务端只发送结构化任务 ID、执行模式和策略，不发送任意 Shell 命令。
- 工作节点声明可用 AI、产品、平台和并发能力。
- macOS 构建任务只能分派到具备对应工具链的 Mac 节点。
- 任务状态与执行状态继续分离。

由于首版已经保留执行记录和触发来源字段，未来增加调度器不需要推翻现有模型。

## 21. 实施阶段规划

### 阶段 0：契约和原型

- 固定任务、状态、执行和权限模型。
- 固定 REST 与 MCP 工具契约。
- 制作 Web 信息架构和关键页面原型。
- 固定本地仓库映射与 Git 策略。

完成标准：核心流程和工具输入输出可以通过文档演练，无关键歧义。

### 阶段 1：最小纵向闭环

- 单用户登录。
- 产品、组件、模块和任务管理。
- SQLite、附件目录和时间线。
- Web 创建和查看任务。
- MCP 读取任务、分析并回写结论。
- 人工验收状态流转。

完成标准：可以创建 `HG-001`，让 AI 按编号读取并回写分析结果。

### 阶段 2：AI 代码处理闭环

- 领取租约和幂等写入。
- 分析、处理、继续、验证和队列模式 Skill。
- 独立 worktree/分支。
- 自动构建、测试、本地 commit。
- 结构化处理报告。

完成标准：AI 可以从任务编号完成代码修改和验证，并推进到待人工验证。

### 阶段 3：Android 管理 App

- Capacitor Android 外壳。
- 系统分享、附件、离线草稿、深度链接和安全存储。
- APK 构建与 GitHub Releases 发布流程。

完成标准：Android App 可完成日常创建、查看、补充和验收任务。

### 阶段 4：反馈 SDK

- Android Kotlin SDK。
- macOS Swift Package。
- 共用 H5 反馈表单。
- 草稿、上下文采集、日志缓冲和附件上传。

完成标准：Android 和 macOS 示例项目都能从 App 内提交带上下文的反馈。

### 阶段 5：开源与可靠性

- 安装、升级、备份和恢复文档。
- 示例配置和示例项目。
- 安全检查、密钥扫描和依赖审计。
- MCP/Skill 跨客户端契约测试。
- Apache-2.0 合规检查、贡献指南和安全政策。

## 22. 首版验收标准

- 可以创建多个产品，并为 Hermes Go 配置 Android、macOS 等组件。
- SDK 或管理端创建的任务拥有稳定编号和完整时间线。
- 两个 AI 同时领取同一任务时，只能有一个成功。
- 用户可以指定“查看、分析、处理、继续、验证”任务。
- AI 可以读取描述、日志、截图和历史备注。
- 分析模式不修改代码和任务状态。
- 处理模式使用隔离工作区，不覆盖用户已有改动。
- AI 回写根因、修改、commit、测试和人工验收建议。
- AI 不能最终关闭任务、删除任务或执行 SQL。
- 人工可以验证通过或失败；失败后完整保留历史。
- Android 和 macOS SDK 都可以通过 H5 提交反馈。
- 真实服务器和本地敏感信息不出现在 Git 历史中。
- 数据库和附件可以完整备份并恢复。

## 23. 测试策略

- 领域单元测试：状态机、权限、编号和租约。
- API 集成测试：认证、幂等、附件、并发领取。
- MCP 契约测试：工具 schema、错误码和权限矩阵。
- Web 端到端测试：创建、筛选、补充、验收。
- Android 外壳测试：分享、附件、草稿和登录恢复。
- Android SDK 示例项目集成测试。
- macOS Swift Package 示例项目与构建测试。
- 安全测试：越权、提示注入、路径穿越、恶意附件和日志泄密。
- 备份恢复测试。

跨 AI 客户端测试顺序建议先完成 Codex，再验证 Claude Code 和 Hermes 适配；不同客户端差异由薄适配层处理，不修改核心 MCP 语义。

## 24. 主要风险与应对

| 风险 | 应对 |
|---|---|
| AI 客户端对 Skill/MCP 支持细节不同 | 保持 MCP 标准化，为每个客户端提供薄适配和契约测试 |
| 反馈内容诱导 AI 执行危险操作 | 将内容标记为不可信数据，限制工具、目录和 Git 权限 |
| SDK Token 被从开发包中提取 | 仅授予提交权限、限定产品、限流并支持快速吊销 |
| 视频附件过大或 AI 无法理解 | 首版限制大小，人工可查看，AI 按客户端能力尽力分析 |
| SQLite 后续扩展受限 | 保持数据访问和迁移边界，未来增加 PostgreSQL 适配 |
| 本地附件丢失 | 强制备份数据库与附件目录并做恢复演练 |
| AI 中断导致任务长期占用 | 使用租约、心跳、幂等和可恢复执行记录 |
| 多任务修改同一仓库产生冲突 | 每任务独立 worktree/分支，限制并发和组件范围 |

## 25. 不阻塞首版的待定事项

- Android 自动更新方式。
- 系统推送通知渠道。
