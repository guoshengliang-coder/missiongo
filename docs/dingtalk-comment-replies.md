# 评论提醒与钉钉快捷回复

评论提醒使用现有企业内部应用机器人、账号绑定和通知队列。项目的“待验证通知”开关不影响评论提醒，评论提醒没有关闭开关。只在明确 @ 或回复评论时触发；明确 @ 的接收人全部保留，包括主动 @ 本人及“所有人”范围内的本人。回复自动提醒直接被回复评论的关联账号，只有这部分自动提醒排除发送者本人；与本次 @ 合并去重，不广播整个讨论组。未 @ 的普通评论不会默认通知发起人，回复自己的评论也不会默认提醒自己。

## 配置独立评论卡片

现有待验证卡片继续使用原模板。评论快捷回复需要在钉钉卡片平台为同一应用创建独立的互动卡片高级版模板，发布后将模板 ID 配置到服务器的 `DINGTALK_COMMENT_CARD_TEMPLATE_ID` 并重启服务。应用需要机器人单聊发送和卡片创建投放权限（`Card.Instance.Write`），目标人员必须在应用可使用范围内，并在 MissionGo 中完成钉钉绑定。

仓库提供可直接导入卡片搭建器的独立模板 [`dingtalk-comment-card.template.json`](./dingtalk-comment-card.template.json)。模板包含普通文本展示、多行输入、本地草稿、回传请求及保存后的显隐控制；示例内容与链接均为虚构数据，不包含应用或线上模板标识。导入后核对预览，再发布并配置服务器。

模板需要以下字符串变量，均为普通文本，评论内容不得参与动作、链接或表达式的构造：

| 变量 | 内容与绑定 |
| --- | --- |
| `headerTitle` | 条目编号与“评论提醒” |
| `itemTitle` | 条目标题 |
| `author` | 评论者；Agent 评论保留 Agent 署名及授权账号 |
| `commentText` | 当前评论正文，使用普通文本组件显示 |
| `parentText` | 被回复评论的预览，空时隐藏 |
| `contentHint` | 正文因平台长度限制截断时的说明，空时隐藏 |
| `itemUrl` | “回条目回复”按钮链接，定位到对应评论 |
| `replyStatus` | 提交结果，初始为空 |
| `replySaved` | 初始字符串 `false`，保存后为字符串 `true` |

在卡片内添加多行文本输入，组件唯一 ID 为 `replyText`，输入事件更新本地普通文本变量 `replyDraft`。添加“发送回复”按钮，动作类型选择“回传请求”，回传参数配置为：`action` 是常量 `reply`，`replyText` 绑定本地变量 `replyDraft`（输入框最新值）。按钮动作 ID 可设为 `send_reply`。输入框及发送按钮在 `replySaved` 等于字符串 `true` 时隐藏或禁用；显示 `replyStatus`。单张接收人卡片只接受一次成功提交，后续讨论使用新收到的回复卡片或进入条目继续回复。

“回条目回复”按钮始终可用，直接绑定 `itemUrl`，不要把评论正文作为 URL。配置后先通过测试条目验证手机与电脑钉钉的输入、提交、结果反馈和跳转，再正式使用。模板需在钉钉卡片平台搭建，并完成发布与真实客户端验证。

未配置评论模板时仍通过机器人 ActionCard 发提醒，按钮打开条目回复，不提供卡片内输入。配置了模板但发送失败时明确记录失败，不自动切换通道重复发送。未配置应用或人员未绑定时评论仍保存，通知记录展示未发送原因；有项目操作权限的人员可在核对后补发。

## 回调与身份

服务器通过钉钉官方 Stream SDK 使用当前应用凭据建立连接，仅订阅 `/v1.0/card/instances/callback`。创建评论卡片时显式设置 `callbackType: STREAM`、`userIdType: 1`，无需新增公网回调路由。仅在评论模板和机器人配置齐备时启动连接；应用配置变化或服务停止时断开旧连接。

卡片的 `outTrackId` 使用持久化通知任务 ID，服务端据此找到原条目、原评论与接收人。接收回调后核对组织、用户类型、企业 userId、绑定版本、应用版本、账号有效性和当前项目查看/评论权限，再调用与 Web、MCP 相同的评论保存逻辑。回调不接受任意条目或评论 ID，也不把钉钉显示名当作登录身份。

输入参数从官方回调的 `content`（兼容旧 `value`）中的 `cardPrivateData.params` 读取。仅处理 `action=reply` 与非空 `replyText`。回复以绑定用户的人工身份保存，标记直接回复对象及讨论根；普通机器人聊天消息不进入评论。用户失去项目权限、解除绑定、原评论撤回或条目转移后拒绝创建回复。

每张接收人卡片使用稳定幂等键，网络重投、重复点击或卡片结果刷新失败不会重复创建评论或通知。只在数据库事务成功后向卡片返回“回复成功”。保存成功与卡片刷新成功是两个不同结果：结果刷新失败时仍可回条目查看已保存的回复。

## Web 与 MCP

Web 输入 `@` 搜索项目内有效人员，可以主动选择本人并创建通知任务；保存成功不等于钉钉已送达。评论正文已经含有的 @ 名称不再单独重复显示，正文未写出的显式接收人以简短“提醒”说明保留。“所有人”仅展开为当前 Builder 与可识别提需者。编辑或删除已选择的 @ 文本会同步移除接收人。旧评论各自作为讨论根；回复在根评论下按创建顺序显示“回复谁”。撤回保留占位与已有回复。

评论使用独立的作者、时间和正文层级；“回复”直接显示，复制评论链接和撤回收进更多菜单。回复输入区显示被回复作者与原文摘要，支持定位原评论和取消回复。原评论撤回或不可访问时保留草稿并暂停发送；用户可以重新选择回复对象，或明确选择“改为新评论”后发送。转移条目的历史评论只读。

提醒结果紧邻对应评论，展开后显示每位接收人的状态与原因；全部成功才显示“钉钉已接收”，不把它当作已读回执。展开时按条目和评论读取通知记录，不受条目概览最近 100 条记录的限制。查询仍验证项目查看权限和评论归属，补发仍需项目操作权限；结果不明时先确认可能重复再补发。不会自动重发历史评论。

MCP 用 `get_comment_candidates` 读取指定条目的候选账号；`append_comment` 支持 `mentionAccountIds`、`mentionTargets`（`proposer`、`builder`、`all`）和 `replyToCommentId`。字符串中的 `@姓名` 不触发通知。Agent 只在用户明确要求提醒或针对性回复时使用这些参数，普通进度评论不广播。

## 讨论浏览与草稿

处理记录支持“讨论 / 全部动态”两种视图，初始仍为全部动态。讨论视图只展示评论组，按组内最近一条评论的时间倒序；全部动态保留原有顶层历史顺序。组内回复始终按创建顺序排列，并保留具体被回复对象。超过 3 条回复时默认仅显示最近 2 条，根评论仍显示；展开全部或收起不会改变讨论关系。评论链接和输入区的原文定位会切到讨论视图，展开目标所在组并聚焦目标，不引入已读或未读判断。

评论草稿只保存在当前浏览器，按登录账号与条目隔离，包含文字、明确选择的 @ 接收人及回复对象；切换条目或刷新后恢复，不自动提交。恢复时核对 @ 文本与 token 位置，服务端提交时仍重新验证接收人和回复权限。发送失败保留草稿，成功后只清除对应条目的草稿；旧条目的异步发送结果不会清除当前正在编辑的另一条目。发送时将请求指纹与幂等键一并保存；服务端已保存但回执丢失时，刷新后重试相同内容仍使用同一键，不重复创建评论。明确取消链接回复会去掉当前 URL 的评论参数，避免刷新后把新评论草稿重新改回原回复。

文件字节与上传凭据不进入草稿存储。上次选择的附件只保留名称用于提示，重新进入时明确要求重新选择，处理前暂停发送；也可明确选择不再添加，不能把文件名显示成已恢复的附件。正在发送或当前有未持久化文件时保留离开页面保护。存储不可用或空间不足会显示未保存提示，当前文字继续留在编辑器中。

## 验证范围

自动化验证使用虚构应用、账号与卡片回调，覆盖权限、讨论关系、通知去重、撤回、账号绑定变化和重复回调；不会给真实钉钉用户发送测试消息。实际模板发布、应用权限及客户端体验需要配置后真实联调，不能以自动化通过推断已经上线或已送达。
