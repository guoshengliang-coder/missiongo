# 交付确认与待合并批次

AND-423 不增加条目业务状态。开发 Agent 完成用户约定的开发和验证后，通过
`propose_merge_delivery` 提出一次明确交付。控制台与条目会话面板共用 `DeliveryCards`，
用户选择“确认完成，等待合并”才加入清单，选择“继续调整”撤回交付。
两者都不改变条目状态，不执行 Git 操作或发布。

项目筛选右侧的“待合并 N”打开本账号在当前项目的已确认交付清单。
用户选择交付、设备、Agent、模型及原生权限；“合并后发布”默认不选。
点击“开始合并”通过现有项目会话启动流程创建专门会话，冻结交付 ID、revision、
PR、head、目标分支、产物与执行配置。执行设备须支持项目会话，仓库映射及模式
由现有派单门禁检查。第一版支持 GitHub PR；本地未推送改动与其他 Git 托管不进入清单。

## 不变量与恢复

- 原开发会话的领取授权、处理轮次、条目内容版本和 Builder 必须仍然有效。
  新的人类输入使交付确认失效。开发会话改变 head 须重新确认；新协议批次的必要集成修复按下述预留与登记流程记录，原确认不覆盖。
- 清单检查证据由执行端读取 GitHub 后上报，服务端不持有用户的 GitHub 凭据，
  不宣称能实时轮询所有 PR。旧证据超过五分钟、失败、冲突、未知或依赖未结束时
  仍可选择有效的已确认交付，交给合并会话核验；这些提示不代表允许实际合并。
  CI 排队或运行时保留原批次等待，状态未变时降低轮询频率；真实失败、冲突或依赖未结束阻止实际合并。
  原开发 Agent 可刷新同一 head 的证据；集成会话不得借用原开发身份。
- 开始批次是事务操作，数据库唯一索引保证同一项目只有一个活动批次。
  同一请求键和相同选择复用批次；改变选择或配置不能复用旧请求键。
- 合并前 Agent 必须重新读取批次及实时 Git/CI 证据，合并带
  `--match-head-commit` 绑定已核验 executionHead，不得使用管理员绕过或纳入未知新 head。
  批次锁约束本入口，不阻止用户在 GitHub 或其他会话手动操作。
- 超时、断线、排队中、丢失响应不是完成。重试回原批次/会话；启动前安全取消后的
  重试允许派单 ID 改变，但会话 ID 不变。已启动或结果未知的会话不自动重建。
- 合并会话不领取源条目。`report_merge_batch` 只允许批次派单记录所选交付已登记执行版本的结果，
  合并证据经执行端核实后才受限交接为开发完成。已成功结果重复提交不会重复交接；
  失败项留在处理中。全部结果明确且外部执行结束后才允许 `finish_merge_batch` 释放锁。
- 若用户选择发布，仍执行 [发布覆盖门禁](release-coverage.md) 的全量候选流程，
  不以本批选择缩小范围。发布交接及最终人工验收保持原有契约。

条目列表与会话列表共用 `MergeProgressBadge` 和交付查询，复用 `item-handler-badge`。
仅有效的人工确认显示“待合并”，活动批次显示“合并中”；提议、撤回、确认失效及已合并不显示待合并标签。
标签按当前账号、项目的交付记录派生，不新增业务状态，轮询与确认操作刷新共用缓存。

## 验证

`scripts/merge-delivery.mjs` 只读取 PR 证据并输出带固定 head 的合并参数，不执行合并。
已合并 PR 还须 fetch 目标分支并验证真实 merge commit 的祖先关系。
脚本测试在临时 Git 仓库真实合并两条独立分支，并拒绝未集成提交。
服务端回归覆盖权限、确认失效、过期证据、幂等键、项目互斥、启动重试、未知结果和部分成功。
浏览器测试覆盖共享卡片、弹窗、响应丢失重试、草稿、320px/1440px、明暗主题、三档字号及对比度。
这些测试不操作生产 PR 或发布环境。

## 整批集成协议（第一轮）

新 Web 入口在显示必要修复授权说明后发送 `integrationProtocol: 1`。没有可核实修复授权的旧入口或旧批次不能静默升级；PR #469 历史授权按下文精确恢复。批次 JSON 增加可选 integration，数据库原有 JSON 容器兼容，不迁移旧数据。

整批计划包含所有交付的当前 head、依赖、顺序、分组、重叠分析理由、每项验证和最终组合验证目标。依赖顺序、重复/遗漏交付和版本由服务端检查，分析内容由执行 Agent 根据真实仓库证据填写。系统不自动从文字推断依赖，不宣称自动规划算法已经存在。

`record_merge_integration` 只有明确领域动作（plan / progress / prepare_repair / repair / cancel_repair / check / final_validation）。每次写入绑定账号、有效批次会话、产品 operate/AI 权限、expectedRevision 和幂等键。计划历史、修复链、阶段、检查及操作记录持久保存；未知结果保留批次与修复预留。相同键改参数拒绝；安全派单重试沿用原会话身份。

原始 delivery.head 不变。每项保留 originalHead 与执行 head；prepare_repair 绑定当前 head 和 base，repair 绑定预留及完整提交链，更新 executionHead 并清空旧检查。cancel_repair 仅处理已证实未推送且无后台执行的情况。服务端没有 Git 凭据，Git 真实性仍由执行端读取并负责；只读脚本验证远端身份、祖先及提交链，不能把用户提交或外部新 head 纳入修复。GitHub 分支保护和精确 head 合并保持。

新批次交接要求完整计划、依赖已合并、最终执行 head 的新鲜本地与远端检查通过。每项成功合并会清空其他未完成项的检查，外部主线变化由执行脚本 expectedBase 核验，须重新验证。最终目标分支组合验证绑定整批实际结果；没有这份记录不能关闭含已合并项的批次。blocked 不代表未知结果；部分失败不自动发布。

控制台会话与待合并弹窗共用 IntegrationProgress，显示计划、顺序、分组、依赖、每项阶段和修复/验证详情；保留原确认与修复记录，刷新或重连不丢进度。不新增条目业务状态或计划批准步骤。旧批次明确显示原授权边界。

验证包含服务端三项相关交付（依赖、回归修复、CI 等待与独立项）、幂等恢复、权限和范围变化；临时真实 Git 仓库验证重叠文件冲突修复、提交链及外部提交拒绝；浏览器覆盖 320/1440px、明暗、三档字号、草稿和刷新恢复。它们不代替真实 Agent / GitHub 端到端试运行；本轮不减少现有 GitHub 主线检查，不包含第二轮检查证据复用。

历史兼容：PR #469 创建的活动批次，只有原始 free_session_starts 记录与该版本服务端完整模板及批次身份精确匹配，才恢复既有修复授权。读取返回 recoveredAuthorization（原 dispatchId 与摘要），首次受限写入持久保存；不匹配、缺失或已结束的批次不升级。原请求幂等参数不因恢复而变化，不读取评论或模型文字作为授权。历史修复仍须核实 Git 后登记完整链；不自动认可变更后的 head。

## 原批次对账恢复（AND-439）

控制台每个批次（包括旧协议及已结束批次）提供「查看对账与恢复」。GET 预览不写库，显示原冻结 head、当前执行 head、执行端登记的实际 Git 结果、每条业务状态与阻碍；服务端不持有 Git 凭据，不把观察当作实时查询。

执行端用 `get_merge_reconciliation` 获取快照，再用 `request_merge_reconciliation` 准备明确动作。人工通过浏览器或 `request_merge_reconciliation_approval` 的原生回执批准该请求后，原批次派单通过 `apply_merge_reconciliation` 执行。MCP 不接受 Agent 参数批准；原生工具只等待绑定快照、请求和动作的客户端人工确认。每次操作实时核对账号、产品权限、原会话及快照；相同请求键参数变化拒绝，响应丢失重复执行不会重复交接。已结束批次的重新激活受项目互斥、活动会话和待执行命令约束。

恢复记录追加在原批次 JSON 中，不覆盖冻结确认、旧结果和人工事件。accept_merge 保存外部实际 head/merge commit；原修复预留若由外部合并结清，单独保留到审计历史，不登记成本会话修复。retry_blocked 保存旧结果后恢复执行。Git 合并事实先记录，逐条开发交接使用独立事务；部分失败保留其他成功。retry_handover 经人工确认仅补充缺失且不冲突的依据，绑定当前开发完成事件和处理轮次；新增事件 `delivery_evidence_added` 不改原人工事件。候选清单和发布交接使用同一有效证据解析器。旧记录缺少逐条快照时仅在原整体 scope 仍精确一致时恢复；不通过猜测升级旧授权。

`record_merge_combined_validation` 绑定全部实际结果及真实目标分支验证，结果改变失效。finish 除逐条交接和预留外，还检查已选发布的同轮次 PR、receiptDigest、deployedCommit 和完整产物交接。人工可明确暂不发布，或允许部分合并后发布；决定绑定当前结果，不改变 publish 原选择。发布仍执行全量候选覆盖门禁。待验证/已完成保持，打回、重开、取消、暂缓、转交及范围变化不能被旧交付恢复。最终验收仍只由人工执行。

Git 只读入口：`node scripts/merge-delivery.mjs --reconcile <delivery-json>`。输入原冻结 head 及已实际完成的 validation；脚本核实实际远端目标引用、PR MERGED、merge commit 在目标上及原 head 在实际 PR head 中。它不执行本地测试、不批准恢复、不修改业务数据。普通合并证据也独立查询目标分支引用，拒绝 PR base 字段滞后和采证期间目标变化。

新增契约均是限定领域动作，不提供 SQL 或任意字段编辑。无恢复能力的旧客户端可继续正常交付；遇到需恢复的场景应升级，不能靠替换 head、借用开发凭据或重建批次绕过。

## 仅补条目交付证据

用户授权的当前产品会话可以使用 `supplement_release_evidence` 补齐开发完成条目的集成引用及完整发布范围，无需原合并身份或独立审批。绑定当前 revision、开发完成事件、轮次，并检查内容与 Builder 未改变；只追加缺项，冲突拒绝。原批次的结果、历史审批及冻结 head 不变。发布前刷新候选，正常执行全量覆盖检查。

已发布的完整产物也可通过 `submit_release_batch` 原子补证据并交接；完整 releases 明确声明历史缺失的必需范围，执行端必须独立核实全部产物及部署前置。发布校验失败则整条回滚，重复请求不覆盖人工打回。不能用此入口接纳外部批次结果、解除 blocked、改变发布选择或验收通过。

### 原生恢复确认（AND-443）

原生确认明确声明人工已核实没有未结束或结果不明的外部操作，不能传 noExecutionRemaining=true 冒充核实。批准与来源回执原子保存，拒绝/取消无领域副作用。确认本身不执行恢复、Git 或发布；原派单仍通过 apply_merge_reconciliation 执行，保留快照、项目互斥、人工返工与发布选择限制。网页/原生竞争时复用已有决定，过期范围不能因重试恢复授权。
