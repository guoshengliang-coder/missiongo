# AND-409：处理中条目显式交给 Agent 接手

人工开始处理会创建独立人工执行。新会话关联、方案批准、原生连接与实际执行授权各自独立，不能仅因为条目已经「处理中」就创建新的执行凭据。

> AND-432：条目详情页常驻的“交给 Agent 接手”入口已移除，不新增替代入口；保留底层交接能力、待接手提示及历史记录。以下人工流程记录 AND-409 的原设计，不代表当前详情页仍提供该入口。

## 原人工流程（历史设计）

1. 在条目详情的执行记录点击「交给 Agent 接手」。Builder 和业务阶段保持不变。
2. 展示全部旧执行（AND-414）：历史记录、离线或过期状态仅告知风险，不要求停止证明；新鲜的活跃回合、运行/停滞状态、未处理命令和未完成启动继续阻塞。接手不停止旧进程。
3. 选择机器和 Agent 发起新派单；或让终端 Agent 先通过 `request_plan_approval` 登记明确方案，再选择本账号、同项目的原会话。外部方案仅产生审批关联；项目会话复用其派单身份，领取前不创建处理关联。
4. 交接授权与当前方案批准分别保存。接手 Agent 仍调用 `claim_item`，取得真实凭据之后才开始实施。

交接授权本身不代表执行已经交接。领取成功才消费授权，写入 `execution_taken_over`，以同一事务使旧执行凭据失效、将被接续的执行关系记为已交接、保留当前业务轮次并签发新凭据。人工核实和旧会话历史保留，不伪造会话完成或进程退出。

## 领域接口及边界

`POST /api/v1/items/:itemKey/agent-handoffs` 只接受人工 Cookie。参数为 `expectedRevision`、非空 `note`、`idempotencyKey`，以及 `target`：

- 原会话：`{kind: "session", sessionId}`，仅使用交付信息中列出的候选。
- 新派单：`{kind: "dispatch", nodeId, agentKind, mode, model?, effort?}`。

服务端重查当前 Builder/交付管理、产品操作和 AI 权限、执行资格、同账号目标、项目、状态、内容边界与所有旧执行。新派单与授权在同一事务建立，普通派单接口不接受接手例外参数。候选只包含本账号、同产品、已登记有效明确方案的审批关联或尚未关联该条目的项目会话；不扫描或控制其他账号会话。

`GET .../delivery` 返回 `canHandoffToAgent`、`agentHandoffTargets`、本账号的 `pendingAgentHandoff`。MCP `get_item_context.executionPolicy.pendingAgentHandoff` 同样仅作待接手信息。`claim_item` 的公开参数不变，服务端将原身份与授权绑定。接手返回 `statusChanged: false` 和新的 `executionAuthorization`；相同领取键复用回执，不同身份或重复新键不能再消费。遗失凭据仍用原身份恢复。

迁移 `202611051350` 增加交接记录，不回填历史授权。授权冻结旧工作活动检查点、内容/Builder边界、原轮次和唯一目标。新来源活动、命令、消息、执行更新、目标归档/撤销或范围变化使旧授权无法消费，即使后来再次确认停止也需要新的明确交接。节点拉取、启动许可及 Agent 领取均重新核对；无效授权不启动节点，不能通过普通派单重试继承授权。

## 批准与连接

已通过 MCP 登记明确范围、方案、验证目标的派单和外部会话，可在原通道不可用时保存领域批准。未登记的历史推断方案仍保留原连接门禁。保存批准与继续消息投递分开；不能投递时返回 `continuationQueued: false`，不伪造已送达结果；符合原上下文和授权的离线续办仅补投递一次，送达不明不重发。领取不要求方案批准或原生模式回执，但仍要求有效的人类接手授权及当前执行边界；原生工作权限继续由原客户端执行。

`thread not loaded` 在控制台与条目内面板显示原客户端加载原会话、确认运行环境并重试同步的指引及可展开原始诊断。不会自动恢复外部会话，也不把不可用当作停止证据。
