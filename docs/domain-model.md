# 领域模型

## 账号与权限

```text
账号（Account：邮箱 + 密码 + 可选昵称，角色为管理员或普通用户）
└── 产品权限（account_products，每个产品三个独立开关）
    ├── 查看（can_view）
    ├── 操作（can_operate）
    └── AI 调用（can_use_ai）
```

账号由管理员创建，没有公开注册。管理员访问全部产品并管理账号；普通用户只访问被授予权限的产品，
可以自建产品、归档自己创建的产品，但不能归档别人分享给它的产品。

昵称是账号在评论和时间线上的署名，可以由本人或管理员修改，**都不需要输入密码，也不移动凭据时间戳**
——它是一个标签，不是登录凭据，为改一个标签要密码只会训练人到处输密码，而为改一个标签把人踢出所有
设备更是不成比例。昵称**不唯一**：邮箱才是身份，两个人叫同一个名字谁也没拿走谁的东西。昵称为空时
显示邮箱 `@` 前面的部分，这个回退**在渲染时计算而不回填进库**，所以改了邮箱不会留下一个过期的旧名字。

署名在读取时由 `account_id` 解析出来，不随事件存库，因此改名会一并改掉过去写的东西。被停用的账号
照样解析得出名字——署名回答的是「谁写的」，不是「今天谁还能登录」。创建条目、编辑详情和附件增删
从未记录过 `account_id`，所以那几类事件仍然显示「人工」。

三个开关相互独立，不是递进等级——「能在控制台里读，但 AI 客户端读不到」是一个真实的配置。写入时
「操作」和「AI 调用」都隐含「查看」，所以库里不会出现「能改但看不见」这种行。管理员在控制台里不受
权限行约束（角色即权限）；唯一的例外是 AI 调用：管理员一旦有 `can_use_ai` 行，其 AI 客户端就被这些
行限定，没有行才是全部产品。这一条是为了让 `ADMIN_AUTHORIZED_PRODUCT_IDS` 的收窄在升级后继续生效。

派单配置按账号隔离：`nodes` 和 `dispatches` 都带 `account_id`，一个账号看不到另一个账号的机器和派单。

账号与产品的权限可以从两侧编辑，改的是同一张表：账号维度替换该账号的整套权限；产品维度只改这一个
产品的那些行——从产品那一侧看不到账号在别处还有什么，整套替换会误删没出现在屏幕上的权限。

会话与 AI 令牌不落库，是签名串，各自携带签发时账号的凭据时间戳。改密、停用或删除账号会移动或抹掉
这个时间戳，已签发的凭据随即失效。会话只能这样整体作废，不能单独吊销某一个；AI 授权则另有
`ai_authorizations` 记录，可以逐个撤销——记录不含密钥，只回答「这次授权是否已撤销」。

## 归属关系

```text
产品（Product）
├── 应用平台（Platform：Android、macOS、Web、服务端等）
├── 模块（Modules，仅一层，直接归属产品）
└── 工作条目（Work items）
    ├── 附件（Attachments）
    ├── 评论与事件（Comments and events）
    └── AI 执行记录（Execution runs）
```

产品是用户所认知的一款完整应用。平台表示模块运行或交付在哪一端，例如 Android、macOS、Web、服务端或跨平台共享。模块表示登录、同步、设置、AI 对话等业务或技术区域，仅保留一层并直接归属产品。

代码仓库关联属于后续 AI 执行阶段的规划，当前持久化模型和公开接口不保存仓库信息，更不会保存与某台机器绑定的绝对路径。

以 Hermes Go 为例，Android 和 macOS 应归为同一个产品下的不同应用平台，而不是两个独立产品。

当前实现中，模块的 `kind` 保存所属平台（Android、macOS、Web、服务端、跨平台共享或其他）。平台选项不代表系统已经创建了对应模块；模块必须由用户明确新增，模块之间不建立父子关系。

## 工作条目标识

每个产品拥有一个大写字母前缀和一条单调递增的编号序列。用户看到的编号格式是 `<PREFIX>-<SEQUENCE>`，例如 `HG-128`。

数据库内部还会保存一个不透明 ID。外部客户端应尽量使用用户可读的条目编号。

## 环境信息与附件

每个新工作条目都必须明确所属平台；无法判断时也需要主动选择“其他”。条目还可以保存结构化环境快照，包括产品版本、构建版本、代码版本、系统版本、设备型号，以及数量和长度受限的自定义元数据。Web 管理端支持手动填写和修改这些字段；Android SDK 已能自动采集同一份数据契约，macOS SDK 仍属于后续规划。

工作条目使用结构化报告保存主要说明。主要说明按类型解释为 Bug 的现象描述、灵感说明、需求说明、任务说明或记录正文；复现步骤与发生条件、期望结果、影响范围和发生频率是仅供 Bug 使用的选填字段。旧条目的 `description` 继续保留并作为主要说明的回退值；新建和编辑页面会同时维护结构化报告与兼容描述。

附件元数据保存在 SQLite 中，文件内容保存在配置的本地附件目录中。首版支持图片、视频，以及 `.log`、`.txt`、`.json` 日志。服务端负责生成存储文件名，附件内容只能通过带鉴权的 API 读取，并始终按不可信输入处理。

## 来源模块与受影响模块

- `sourceComponentId`：记录反馈最初在哪个模块中被发现。
- `affectedComponentIds`：记录需要修改或验证的模块。

一条来自 Android 的反馈可能同时影响 Android 平台下的模块、macOS 平台下的模块、跨平台共享模块和服务端模块，不需要拆成多个顶层工作条目。

## 工作条目类型

每条记录统一称为工作条目，类型可以是 `idea`、`requirement`、`bug`、`task` 或 `note`。随着内容逐渐明确，可以修改条目类型，但稳定编号和完整时间线不会改变。

## 工作条目状态机

- `inbox` 在中文界面显示为“草稿”：用于保存信息尚未完整的内容，此时 AI 不得领取处理。
- `ready` 在中文界面显示为“待处理”：表示内容和目标已经确认清楚，可以由人工或 AI 开始处理。

这两层状态用于把“快速记录”和“确认执行”分开，避免一句尚未补充完整的灵感直接进入 AI 处理流程。

```text
inbox
  -> ready
  -> in_progress
  -> on_hold
  -> pending_verification
  -> done
```

人工验收失败后，条目会回到 `ready`，并追加重新打开事件。`cancelled` 是由人工控制的旁路状态。

**从 `in_progress`、`pending_verification`、`on_hold` 或 `done` 回到 `ready` 必须说明原因**，原因写进
`status_changed` 事件的 `note`。从这四个状态退回，意味着已经做过的工作没有站住，而重新派单之后，
下一个接手的人或 AI 只能从这里读到为什么。判定按「来源 + 目标」而不是按 reason：`reopened` 同时用于
`on_hold → ready` 和 `ready → inbox`，只有前者是退回。`inbox → ready` 是首次定稿，不在其中；
`manual_override` 同样不能绕过，否则就留下一条什么都不解释的回头路。

**移到 `cancelled` 同样必须说明原因**（AND-64），不论从哪个状态进入，包括 `done` 经 `manual_override`
直接移过去。条目从此离开队列，之后翻到它的人只能从这条 `note` 知道它为什么被放弃。

`packages/domain` 中的实现是状态规则的唯一权威来源。REST 和 MCP 处理层必须调用它，不能分别复制状态流转逻辑。

## AI 执行记录

工作条目状态与 AI 执行状态相互独立。一个工作条目可以包含多次失败、中断或成功的执行。每次执行保存处理模式、触发来源、AI 类型、时间、处理报告和租约历史。

最早只支持 `agent_pull`，即用户让 AI 主动按编号读取。AND-37 之后增加了管理端派单：控制台勾选待处理条目，
交给一台已配对的机器，机器拉取后启动一个会话处理整批。派单记录在 `dispatches` 和 `dispatch_items` 两张表里，
不写 `ai_executions`——一个会话对应多个条目，且服务端在会话启动之后看不到它的执行状态，写进去只会是半截数据。
`scheduler` 仍然是预留的触发来源：没有定时，派单始终由人点一下开始。
