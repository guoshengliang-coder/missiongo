# AND-367：项目协作与条目依赖

实现依据是条目中确认的 V2 界面与实施方案。保留现有工作区、列表、详情、执行区和设置层级；不增加条目状态，不引入多仓库工作区，不修改 Git 授权机制。

## 业务约束

| 阶段 | 操作与结果 |
| --- | --- |
| 配置 | 接收项目管理员配置允许提需的来源项目、接收模块、默认 Builder；定向授权不推导反向或传递关系。未分配 Builder 时通知项目管理员。 |
| 整理 | 原条目 Builder、项目管理员或其已授权 Agent 整理版本化草稿。草稿只保存在原条目，不创建接收条目，不阻塞交付。 |
| 批准 | 原 Builder 或原项目管理员登录后，审阅请求、证据、附件范围及验收条件，明确批准当前版本。一次事务创建接收项目的待处理条目、依赖、审计和通知。批准人默认是唯一人工验收人。 |
| 处理 | 接收方 Builder 自行安排人员或 Agent，不自动启动对方 Agent。原项目可继续独立开发，但所有开发完成、待验证、已完成入口均受依赖门禁约束。 |
| 交付 | 接收方先在共享详情提供明确交付说明（版本、接口变化、验证步骤与证据），再按既有交付流程进入待验证。通知提需方，依赖保持阻塞。 |
| 验收 | 只有指定提需方人工验收人可确认已完成；接收方 Builder、其他管理员、Agent 均不能替代。验收不通过须说明原因，退回待处理，保留阻塞，新一轮须补充交付说明。 |
| 拒绝 | 接收方 Builder 或接收项目管理员可说明原因后取消接收条目。取消解除等待，原 Builder 决定如何在本项目解决。 |
| 解除 | 接收条目已完成或已取消，或原 Builder 明确撤回依赖，等待结束；系统不会自动推进原条目。 |

同一条目可依赖多条协作，也可继续向其他项目提需。项目间可双向协作，条目依赖图禁止循环（包括完成后可能重开的路径）。所有未撤回依赖都有明确结论后才允许推进交付。

## 权限和数据范围

- 普通条目、搜索、列表、时间线、执行记录和附件入口继续要求原项目权限。协作权限不扩大这些接口的范围。
- 专用共享详情只返回批准的请求、选中附件、接收状态、Builder、指定验收人和明确共享的讨论与处理结果。原条目标题、内部评论、执行记录、其他附件不随协作开放。
- 源码继续使用用户自己的 Git 凭据；本功能不发放 Git 权限。没有代码权限仍可整理协作草稿，提 PR 取决于 Git 平台实际权限。
- 共享附件记录批准时的内容版本。文件替换、删除或所属评论撤回后，不会把新内容自动暴露；需要重新整理、审批证据。
- 普通项目观察者只能读取；共享讨论要求一侧项目操作权限，人工验收人可就其验收任务交流。标记交付说明要求接收方 Builder 或接收项目管理员权限。
- 转交验收人为显式人工操作，需要原因；候选人须能访问所有关联来源项目。同一接收条目的验收人一起变更，避免多人互相覆盖结论。
- 停用接收授权只阻止新提交，已有请求继续处理。接收项目管理员可单独撤销、恢复共享访问；撤销不会自动解除依赖。来源方仍可在不读取共享内容的情况下撤回自己的依赖。
- 管理员配置入口只提供项目 ID/名称目录，不提供其他项目内部信息。跨项目候选人员仅供对应责任转交操作使用。

## 取消、重复和异常处理

原条目取消前，必须对所有未结束协作选择“撤回”或“保留并指定接续负责人”。撤回不取消接收条目，保留不自动改变原验收人；如需更换验收人须另行显式转交。未批准草稿同时失效。可先逐条处理不同处置，再取消原条目。

关联已有条目仅允许当前可读取共享内容、验收人一致、目标项目/模块匹配的协作条目，不接管内部条目。重复请求可先转接到兼容条目，再由接收方决定取消重复条目；转接保留旧依赖及审计，旧接收条目的验收权限不改变。

接收条目重开后，非撤回依赖重新阻塞交付；原条目即使已完成也不自动重开，Builder 根据通知另行判断。没有超时自动解除。含未结束协作的项目不能归档，含协作历史的条目暂不支持迁移，以免丢失权限与验收归属；可保留原条目并建立后续条目。

## 界面入口

1. **项目设置 → 项目协作**：接收授权与可请求项目两页签；管理员编辑接收模块、默认 Builder、启用状态。
2. **条目更多操作**：发起协作请求、关联已有条目。仅对当前 Builder/管理员及允许阶段开放。
3. **执行记录下方 → 协作与依赖**：我在等待、等待我、待人工审核草稿、阻塞提示；打开专用共享详情。
4. **请求弹窗**：编辑 → 预览 → 显式勾选批准；修改内容需要重新确认，失败保留内容，重试复用命令编号。
5. **共享详情与验收弹窗**：讨论、交付说明、撤回、转接、转交验收、共享访问管理、通过/打回。验收冻结打开时的证据版本，变化后旧确认被拒绝。
6. **列表**：协作标记；更多筛选支持发出、收到、等待协作、待我验收，筛选与数量/分页/URL 保持一致。
7. **消息中心**：复用持久化个人消息；待审核、待验收、完成/取消、退回/重开、转交等消息在当前可访问的本方条目中落地。
8. **取消确认**：列出未完成协作，选择撤回或接续负责人，与现有执行处置和说明附件并列。

复用 `Modal`、`Select`、统一浮层、草稿关闭保护、双语文案和设计令牌。手机与桌面保持现有外框和导航。没有新增原生 SDK 界面或原生权限请求；WebView 使用同一 Web 入口。

## 实现与事务

新增迁移 `202611030735`：`collaboration_grants`、`collaboration_drafts`、`collaboration_requests`、`collaboration_events`、`collaboration_receipts`。不重写历史条目或状态。索引覆盖依赖查找、草稿、共享事件；唯一约束保证草稿只提交一次、活动边不重复。

`Collaborations` 服务承载定向配置、草稿审批、关系管理、共享讨论、受限附件和验收。每次命令重新检查账号及项目权限；审批/转接/取消使用现有 SQLite 写事务，审批命令有账号级幂等回执和内容摘要。依赖新增或变化更新相关条目 revision，防止旧取消/交付确认覆盖新依赖。

`collaborationTransitionDenial` 接入统一状态策略及最终写入路径，覆盖普通按钮、手动调整、批量请求、MCP 和系统交接。通知事件和业务变化在同一事务中持久化；消息按业务事件和收件人去重。状态仍以条目为准，不另造依赖状态机。

MCP 新增读取 `get_item_collaborations`、`list_collaboration_targets`、`get_collaboration`、`get_collaboration_attachment`；新增写入 `prepare_collaboration_request`、`append_collaboration_discussion`。没有审批、取消、验收或任意字段写工具。草稿返回审核路径，供 Agent 引导 Builder 查看；读取范围同时受当前 AI 授权和专用共享权限限制。Skill 升级到 5.32.0 并更新内容摘要。
